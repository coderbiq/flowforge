## 真实工作流（用户视角）

用户全程只做一件事：**在 agent 会话里用业务语言说话**。写 Markdown、建目录、跑 CLI 全部由 agent 完成。

### 一次真实推进的骨架（3 天，数据迁移域）

| 阶段 | 用户动作类型（泛化） | Agent 动作（工具流证据） |
|---|---|---|
| 立项 | 提出拆分指令："旧提案太大且有错，把 X 拆出去单独立项，再开一个专题修复 Y 的 proposal" | 读旧 proposal 全部工件与源笔记，新建两个 proposal 目录并写需求事实 |
| 对账 | 质疑既有结论："Z 不是已经做完了吗？" | 解释工件状态、核对文件事实 |
| 设计 | 要求全景 review："避免低级错误"；技术纠偏："这个阶段不应该有 N，应该看模块 M 怎么做"；批准："同意，先落盘在设计" | 写全景评审文档 → 激活 solution-design skill 迭代方案并落盘 |
| 拆票 | "继续"；看不懂就问："不太看得明白这些票在做什么" | 激活 plan skill 生成 7 张带 DAG 的票（全部 agent 写）、跑 check/frontier 展示就绪队列 |
| 执行 | "继续"×N；质疑批次含义；业务纠偏（字段/规则类修正） | 每轮 frontier 取批次、派子代理（含后台批量分析角色）、留证据、双轴审查 |
| 收口 | 新痛点出现时提出新立项 | 进入下一轮 proposal 循环 |

### 用户操作词汇表（按出现频次）

1. **"继续"**（最高频）——推进下一批次；
2. **批准**："同意，继续推进（先落盘在设计）"；
3. **质疑**："不太看得明白…"、"批次 N 是什么？"；
4. **技术/业务纠偏**：陈述自己的理解与期望，指向参照物（"应该看模块 M 是怎么做的"）；
5. **补充环境事实**：告诉 agent 本地有什么数据、可以用什么工具操作；
6. **立项指令**：明确要求创建/拆分 proposal。

零 Markdown 编辑、零手工建目录、零手工 CLI（用户直接敲的只有看进度类命令）。

### 执行侧形态（谁在干活）

- 主会话（旗舰模型）负责 align/design/plan 与汇总；
- 票执行派给子代理或独立执行会话（不同 agent CLI 的专门交付会话，终端现场可见"首批 ticket 交付"类会话）；
- `flowforge check` / `frontier` 由 agent 在推进点自动运行（补救票案例中用于修正 blocker 文本格式与依赖计算）。

## 对文档的修正含义

1. README 快速开始的正确主线是**对话驱动**：安装 → init → agents deploy → 在宿主会话里说出一个需求 → 看 agent 建 proposal、写票、跑 check/frontier → 用"继续/同意/质疑"推进批次 → 收口。CLI 是 agent 的确定性工具，用户只在想直接看进度时自己跑 `status`/`frontier`。
2. 「一个需求如何实际推进」以案例叙事呈现，叙事骨架取自上表（立项 → 对账 → 设计 → 拆票 → 执行 → 收口），**对话引语一律用虚构通用场景**（对外文档采用虚构的"通知系统重构"案例）。
3. 「手写一张票」不是用户路径——票由 flowforge-plan 生成；票的 Markdown 形态最多作为"工件长什么样"的展示，不作为操作指令。
4. 场景篇场景 1 同步：新手路径 = 说出一句话需求，不是写极简票。
