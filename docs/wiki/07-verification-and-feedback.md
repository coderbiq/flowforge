# 07. 验证与反馈：证明交付、记录失败并收敛修复

> 状态：正文初稿，供讨论完善。

前面的任务上下文规定了完成条件，依赖与推进规定了何时可以开始，执行与协作规定了谁在什么边界内工作。最后还需要回答：**这次工作是否真的交付了要求的行为？如果没有，下一次工作怎样获得足够准确的反馈？**

FlowForge 将验证、双轴审查、完成证据和失败记录组成一个反馈闭环。它不把勾选任务、命令退出成功或 Agent 的一句“完成了”单独当成交付证明。

## 1. 验证必须对应可观察的完成条件

任务的 `Done and verify` 应将每个可观察完成条件与精确命令、观察方式和预期结果配对。[1]这使执行者和审查者知道要观察什么，也使“测试通过”不再脱离行为范围。

例如，数据导出任务的验证不能只写 `go test` 通过。它还需要覆盖已确认的权限行为：用户有权访问时可以导出，权限被收回时不能获得不允许的数据；具体命令和测试名称必须以实际项目为准。

执行过程中需要区分几类记录：

| 记录 | 说明 | 是否等于完成证据 |
|---|---|---|
| 预定验证 | 任务准备时约定要运行的命令或观察方法 | 否，尚未执行 |
| Implementation note | 实际完成了哪些 Changes、运行了什么命令、修改了什么文件 | 否，它是给审查者的执行报告 |
| Change 证据四元组 | `cmd`、退出码、关键输出和产物路径 | 是执行事实的一部分，但不覆盖全部审查 |
| Review rounds | 固定变更范围上每轮 Standards/Spec 审查与处置 | 是审查过程记录 |
| Completion evidence | 实际行为、验证结果、发现处置、偏差和实现引用 | 是关闭前的交付证据 |

轻量执行者完成机械动作后，运行列出的检查，勾选已完成 Change，并写 Implementation note；它不调用 Review、不写 Completion evidence、不改变任务状态。[2]这一步的作用是留下可审查的执行事实，而不是提前宣布任务已经完成。

命令失败时，执行者应在报告中保留原始命令、退出码和相关错误输出，不把失败改写成模糊的“测试不通过”。这样下一次处理者可以区分环境问题、调用错误、代码错误与任务事实冲突。

## 2. 审查需要同时看 Standards 与 Specification

Review 针对同一个固定变更范围执行两条独立的轴：[3]

- **Standards 轴：**代码是否符合任务已经转录的项目规范和一般编码标准，并检查明确的工程质量问题。
- **Specification 轴：**实际行为是否忠实满足有效需求、设计和任务契约，包括边界场景、范围和验证条件。

两轴分开，是因为“代码写得符合风格”与“实现了正确的行为”不是同一个判断。一个实现可以通过静态规范检查，却漏掉导出权限；也可以满足功能，却越过 Write set 或违反项目分层规则。

审查应针对固定点和明确 diff，读取当前有效权威、任务、消费修订和适用豁免。测试通过不能替代 Specification 审查：测试通常覆盖已经实现的路径，不能自动证明遗漏的需求也被覆盖。

Review 还会先进行按 Change 的交付核对：任务要求的动作是否真的出现在变更中，实施报告中的证据是否与实际 diff 一致。缺失、部分完成、相反实现或未请求的变更，应先被记录并返回修复，不应让后续两轴审查建立在不诚实或不完整的交付报告上。[3]

## 3. 发现问题后，修复责任不能被混淆

审查发现并不都用同一种方式处理。它们应根据是否改变上游决定和影响范围分流。

| 发现类型 | 处理方式 |
|---|---|
| 在已批准责任和接口内的具体实现问题 | 追加机械的 `Fix:` Change，交给实施者修复 |
| 需要改变模块责任、接口、seam、信息流或验证策略 | 作为 design return，交回 Solution Design |
| 改变可观察行为、范围或外部约束 | 交回 Align，重新确认需求 |
| 严重、跨 Write set、改变验收或影响下游边界的发现 | 建立 repair ticket，原任务进入 `needs-repair` |

Review 不是通过创建一个“以后再处理”的非阻塞任务来隐藏当前缺口。对必须交付的行为，原任务在缺口修复或权威所有者明确处置前不能被当作完成。

对于普通可修复问题，Review 将新的 `Fix:` 动作追加到原任务，下一轮 Implement 执行；对于实质性问题，repair ticket 独立进入 frontier，原任务和受影响下游通过依赖保持不可过早推进。修复通过自己的审查后，再把证据关联回原任务。[1]

这样，反馈不会被埋在审查评论里，也不会依赖主会话记忆。它成为下一次执行上下文可以读取的任务事实。

## 4. Completion evidence 才能支撑关闭

Completion evidence 应记录：实际交付了什么，运行或观察了什么及其结果，两条审查轴的发现和处置，发生了哪些偏差及由谁决定接受，以及实现引用。[1][2]

它默认以内联内容写入任务；当验证跨多个环境或参与者、需要独立生命周期，或内联内容会遮蔽事实时，再提升为独立 evidence 工件。Evidence 不是未来计划，也不是把整张任务复制一遍。

Catalog 对已关闭任务检查是否存在非空 `Completion evidence`；缺失时报告 `missing-completion-evidence`，严格策略会拒绝该项。[4]这是结构事实检查，不代表 CLI 能判断证据是否真实充分。

关闭前至少要满足：

1. 可观察交付已实际验证。
2. Standards 与 Specification 发现已修复，或由有权责任方明确处置。
3. 偏差、延期和阻塞没有被状态字段掩盖。
4. 实现、验证和审查证据能够定位到当前固定变更。
5. 任务的消费依据仍然有效，或者版本变化已经完成复核。

这里需要保留当前工作流的责任差异。完整模式的 Implement 可以在一个连续会话中实施、审查、处理发现并收口；轻量模式则由 Implement 留下报告，Review 负责后续审查和完成分支。不能将“Review 总是关闭”或“Review 从不关闭”当作脱离执行模式的统一规则；应以当前 Skill 约定和调用模式为准。[2][3]

## 5. 失败怎样成为下一次工作的输入

执行失败若只停留在旧会话里，下一位执行者只能重复猜测。FlowForge 要求阻塞时先向任务追加 `Blocked evidence`，记录逐字错误、尝试过的命令和下一步假设，再返回 `STATUS: BLOCKED`。[2]

这段记录不是最终的执行契约。Refine Ticket 消费它：将可验证的失败事实转写到 `Verified contracts`，核实正确调用或当前约束，删除已经消费的临时阻塞段落，并重新运行检查。[5]

如果失败事实显示接口、顺序或责任仍未决定，Refine Ticket 不应猜测答案，而应返回设计或需求责任方。如果只是命令位置或文件坐标过时，且不改变语义，就可以更新任务事实。这样反馈能够修正上下文，而不是只增加一段越来越长的失败历史。

失败记录还应区分：

- **命令或环境失败：**当前检查无法运行，需要修正调用或环境。
- **实现失败：**代码行为不满足既定条件，通常形成 Fix Change。
- **事实冲突：**任务与仓库现状不一致，需要先核实并更新任务或依据。
- **设计缺口：**完成动作要求新的责任或接口选择，返回设计。
- **需求变化：**用户期望或范围变了，返回需求确认。

它们的下一步不同，统一写成“重试”会让接手者再次误判。

## 6. 前端交付还需要运行结果和视觉证据

后端测试可以验证数据和行为，但 UI 还存在代码文字难以完整表达的布局、颜色、层级、响应式和交互结果。对于声明了前端规范与视觉验证入口的任务，前端执行增加一个截图自审循环：先按票据条款实现，运行项目声明的 verification-entry，加载截图，按 counter-example 条款逐项检查，修复后重复验证。[6]

视觉证据应与具体条款绑定，而不是只附一张“看起来不错”的图片。交付时至少要能定位：

- 哪个运行状态和页面被截图；
- 哪些 `must`/`must not` 条款由图片或量化输出观察；
- 自审检查了哪些反例，发现了什么，如何修复；
- verification-entry 的原始输出和截图路径在哪里。

视觉审查还要把截图与量化结果交叉核对，避免输出中的数字与实际画面不一致。截图只覆盖被观察的状态，不能替代所有交互和无障碍验证；没有可运行的验证入口、没有必要的截图或当前宿主无法提供图像能力时，应报告阻塞而不是静默通过。[6]

## 7. 闭环如何回到下一轮推进

验证和反馈的终点不是一条“完成”消息，而是新的可检查事实：任务交付有证据，未解决问题有归属，修复或上游变更已经写进相应工件。随后重新运行 `check` 和 `frontier`，让新的修复任务、解除的依赖和仍然存在的诊断进入下一轮计算。[2]

这一闭环把前面几篇连接起来：任务上下文预先定义观察方法，执行者留下事实，审查分别检查规范与需求，失败记录被消费为新的契约，严重发现通过 repair 或上游返回保持边界可见，队列再依据当前文件重新计算。

它降低了“勾选即完成”“失败即丢失”和“审查意见只在聊天里存在”的风险，但不替代人对需求、证据真实性和交付质量的判断。
