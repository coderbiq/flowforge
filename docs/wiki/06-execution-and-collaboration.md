# 06. 执行与协作：角色、上下文、模型和宿主

> 状态：正文初稿，供讨论完善。

[依赖与推进](05-dependencies-and-progress.md)确定了当前可以考虑执行的任务。接下来还要安排：交给谁、提供哪些输入、允许修改什么、什么时候停止，以及完成后怎样让下一位接手。

FlowForge 将角色定义、执行约定和宿主部署结合起来，支持有界的工作分派。本篇讨论这些协作接口，不重新展开任务契约的准备和交付审查的细节。

## 1. 把一个任务交给一个有明确输入的执行上下文

项目执行策略采用“一票一个新的执行上下文”：批量推进时，每个任务从新子代理或新会话开始，跨任务状态通过文件、结果契约和重新计算的 frontier 传递。[1]

这里的关键是每次执行有独立的工作范围，而不是假定执行者什么都不知道。宿主可能提供继承的背景、项目规则或其他输入；无论怎样继承，任务所依据的有效事实都应当能从工件恢复，不能只靠主会话里未保存的决定。

一次派发应把以下内容说清楚：

| 派发要素 | 执行者需要知道什么 |
|---|---|
| 目标与输入 | 当前任务路径、项目位置，以及关联需求、设计和前序证据 |
| 工作边界 | 本次交付范围、执行模式、Write set 与相关约束 |
| 验证与返回 | 需要运行的检查、输出位置及结果契约 |
| 停止条件 | 信息冲突、无法验证、需要改变设计或范围时怎样返回 |

入口阅读从项目规则、任务及链接的有效依据开始，再读取具体修改位置。它不是要求执行者重新调查整个项目，也不是只提供一句任务标题后让它自行补全上下文。

例如，后台导出的权限查询能力已经由前序任务交付，当前执行者接手“将其接入导出流程”时，需要读到该能力的接口依据及实际交付证据。主会话一句“权限模块做好了”，不能替代这些输入。

## 2. 角色分工决定谁解决哪类问题

FlowForge 的角色定义包含职责、默认 Skill、边界和返回约定。角色用于明确责任，不只是给同一个通用提示换一个名字。[2]

| 工作性质 | 相应职责 | 遇到什么情况需要交还 |
|---|---|---|
| 需求分析 | 确认可观察结果、范围、场景和约束 | 产品取舍需要用户或相应责任方确认 |
| 方案设计 | 确定责任、接口、信息流和验证策略 | 新发现改变业务行为时返回需求环节 |
| 任务规划与准备 | 将既定决定组织成执行增量，补齐事实 | 仍有设计选择或无法核实的前提时返回对应环节 |
| 实施 | 在批准的边界内交付当前任务 | 需要改变接口、责任、范围或验收行为时停止自行决定 |
| 审查 | 对固定范围的交付进行核对并处置发现 | 需要上游决定时明确交还，而非自行改写要求 |
| 有界调查、批量提取或机械执行 | 收集事实、整理材料、执行已明确的动作 | 不代替跨组综合与最终取舍 |

主会话承担用户沟通、任务链安排、结果综合和下一步路由。它可以将独立可验证的工作委派出去，但不能把尚未澄清的决策责任隐藏在派发提示中。

角色分开也不意味着任何小任务都要启动多个 Agent。简单、紧凑的工作可以由一个具备相应能力的会话完成。委派需要准备输入、读取材料和综合结果，应当有明确收益，而不是增加形式上的交接次数。

## 3. 执行模式决定本次会话做到哪一步

FlowForge 区分轻量模式与完整模式。模式由任务准备或调度环节明确，执行者不能因为遇到困难就自行扩大职责。[3]

| 模式 | 本次执行承担什么 | 结束时交回什么 |
|---|---|---|
| 轻量模式 | 按已定动作修改，执行机械检查，记录实现情况与结果 | Implementation note、完成与未完成的动作、验证结果和阻塞；不自行审查或关闭任务 |
| 完整模式 | 在预先约定的边界内实施，调用审查并处理发现，完成证据与收口 | 可核对的交付、审查处置与完成依据 |

两种模式都不能把需求或设计缺口当作普通编码细节。尤其是轻量模式，指令含糊、代码事实与任务冲突、或必须重新选择方案时，应保存现场与失败事实，再返回调度者安排调查或决策。[2][3]

执行角色也有重试和预算约定，目的是避免持续重复同一种失败。当验证无法通过时，应说明已试过什么和当前卡点，而不是不断增加尝试后只汇报“仍未完成”。具体错误记录和修复闭环在[验证与反馈](07-verification-and-feedback.md)展开。

执行模式不是模型名称的别名。能力较强的模型也可以遵守轻量模式，换一个更强模型也不会自动获得改变接口、需求或范围的权限。派发者需要同时检查任务模式、角色约定和具体提示是否一致，不能把不同来源的提示拼接后就假定它们没有冲突。

## 4. 结果契约与会话交接让工作可以接续

执行角色返回时使用结构化结果：状态，以及 Summary、Changed Artifacts、Verification、Findings or Blocker、Next Action 等信息。[2]调度者据此知道本次会话完成了什么、有什么依据、下一步应该交给谁。

需要区分三个层面：宿主报告某次运行结束，角色返回了完成状态，以及任务符合交付关闭条件。它们不是同一事实。轻量执行者可以完成本轮动作并返回，任务仍需后续审查；一段成功退出的脚本也不能代替实际交付证据。

正式结论、任务变更和验证事实应保存在对应工件中。结果消息提供定位与概要，不应成为唯一记录。会话 handoff 则补充下一次会话无法从这些文件直接恢复的信息，例如当前调查卡点、尚未结束的尝试和建议入口。[4]

当前 Handoff Skill 要求链接已有需求、设计、修订、任务与证据，避免复制成另一套权威；交接文件存放在操作系统临时目录，并去除敏感信息。[4]因此，临时 handoff 适合恢复会话，长期需要保留的知识仍应写入正式工件。

## 5. 批次、并行与隔离是不同的安排

一次 frontier 可能给出多项候选，调度者仍需决定执行顺序和并发方式。图上没有依赖，只意味着未声明相互阻塞，不说明共享代码、测试环境或其他资源没有冲突。

例如，“接入权限查询”和“完善失败提示”在既定设计下可以独立交付，但如果两者都修改同一个导出处理器，就需要协调写入。可以安排顺序执行，或在隔离工作区中实施后明确集成责任。使用隔离工作区也不能消除合并冲突和集成验证。[1]

只读调查、独立材料提取等工作较容易并行；修改共享文件、持有同一资源或依赖对方最新实现的工作，需要更严格地安排输入和写入边界。

当前 `frontier --pi-workflow` 生成的是逐票使用 fresh 上下文、携带 `flowforge check` gate 的顺序脚本，遇到未完成的运行结果就停止。[5]这是一个具体的批次执行机制，不应描述成“frontier 会自动并行完成所有任务”。角色返回、gate 与业务交付仍需按各自约定检查。

## 6. 模型与宿主配置怎样支持这套分工

角色说明工作责任，模型配置选择承担工作的能力，宿主提供工具和执行环境。将三者分开配置，使同一套任务与方法能够在不同运行条件下使用。[6]

### 按工作需要选择模型

FlowForge 支持按能力配置组、角色和宿主设置模型及推理强度。二者分别解析，因此可以只为某个宿主替换模型，而保留统一配置中的推理强度；显式的继承设置则交由宿主处理相应字段。命名的 model-set 可以集中切换一组配置并重新部署角色。[6]

这种能力支持按任务需要配置：设计与复杂审查需要判断能力，机械执行需要稳定的工具使用，视觉任务还需要相应的视觉能力。但流程本身不证明某种模型一定够用，也不保证低价模型最终更便宜。任务准备、审查、重试与返工都属于整体成本。

模型配置只是期望的运行安排，还应核对宿主能否识别模型标识、是否具备所需工具与权限，以及本次实际派发是否采用了目标配置。

### 将角色部署成宿主能够使用的文件

FlowForge 可以将角色定义编译到 Claude Code、OpenCode、Codex 和 PI 的原生目录。`agents status` 检查角色部署状态，`assets verify` 比较受管 Skill 与规则，帮助发现缺失或漂移。项目配置及部署产物按本机管理，减少多人多机之间的模型配置互相覆盖。[1][6]

部署成功不等于各宿主提供完全相同的运行保证。Write set 是任务边界；具体工具白名单、测试文件保护和扩展拦截需要宿主支持并实际启用。不能把提示中的“不得修改”写成所有环境都强制阻止。

配置切换也有恢复边界：当前 model-set 切换失败会恢复激活指针，但写入产物时发生 I/O 错误，仍可能留下部分更新，需要检查部署状态。[6]这类环境问题应明确报告，而不能当作任务本身已经失败或完成。

## 7. 协作的结果要回到可检查的交付

一次可靠交接应使接手者知道目标、输入、边界、实际结果与下一步，而不必继承整段会话。角色和模式限制临场越界，模型配置匹配工作能力，宿主部署则让这些约定在具体工具中可用。

这些机制组织了执行过程，但不替代结果核对。下一篇将说明，如何将测试、审查、失败记录和修复连接起来，判断一项交付是否真正符合有效要求。
