# 04. 任务上下文：把需求、设计和规范交给当前工作

需求和设计已经确认后，执行者仍然需要知道：本次交付什么、在哪里修改、必须保留哪些行为、怎样验证完成。FlowForge 通过任务准备，把分散的全局依据组织成当前工作的局部执行契约。

这里的“契约”指执行者与准备者共同使用的明确约定。它既包含要做的动作，也包含动作成立的前提、允许修改的范围和可检查的结果。任务文件因此承担上下文入口的职责，而不仅是记录名称与完成状态。

## 1. 先确定一个可以验证的交付增量

Plan 从有效需求与设计出发，选择一个范围受控、能够独立验证的增量。划分依据是交付行为及真实依赖，而不是每个文件都对应一张任务。[1]

例如，在前文的数据导出方案中，“实现后台查询”不足以定义交付。更明确的增量可以是：**后台导出在执行时重新判断请求者的数据权限，查询结果不超出当时允许访问的范围。**它可能涉及任务参数、鉴权调用和查询过滤几个位置，但共同完成一个可验证行为。

准备这个任务前，权限判断时机、责任与接口已经由需求和设计确定。Plan 需要将这些决定落实为任务，不能把“选择合适的鉴权方案”当作一个实施步骤。如果仍需决定接口责任、跨模块顺序或验证策略，应返回设计环节。

任务之间只声明真正阻止开工的依赖。范围很小且没有独立交付价值时，不应为了减少单张任务的字数继续拆分；大规模迁移则可按兼容引入、逐批迁移、最后移除旧实现安排。依赖如何计算将在[下一篇](05-dependencies-and-progress.md)展开。

## 2. 三层信息怎样组织同一项工作

FlowForge 的任务约定使用三层结构，让人能够快速判断交付，同时让执行者获得具体坐标和细节。[1][2]

| 信息层 | 主要内容 | 解决的问题 |
|---|---|---|
| 第一层：交付与局部设计 | Delivery、Design context 及来源链接 | 人能迅速理解任务价值，执行者知道本次动作依据什么 |
| 第二层：共同执行约定 | Touch points、Changes、Constraints、Write set、Done and verify | 明确位置、步骤、边界、允许修改范围和完成条件 |
| 第三层：执行细节 | 已核实契约、执行场景、预期测试、产物关系、局部约定 | 补齐正确实施所需的仓库事实与容易漏掉的条件 |

这三层属于同一份任务文档，不是三套独立规格。每条信息应有清楚的作用，避免在不同段落反复复制上游全文。

### 位置、动作和边界需要能相互对应

Touch points 给出文件和符号坐标，Changes 描述在这些位置要实施的具体动作。Constraints 保存本次必须遵守的不变量；其中的 Write set 列出允许修改的文件或目录。

仍以导出任务为例，任务应将“重新判断权限”连接到实际鉴权接口，将“限制查询范围”连接到实际查询入口。如果动作需要修改某个接口，却没有允许修改对应位置，准备者应先处理这个矛盾，不能把它留给执行者自行扩大范围。

Done and verify 则把完成条件与具体命令或观察方式、预期结果配对。“测试通过”过于宽泛；准备时需要说明哪些检查能够观察权限变化后的导出行为。测试名称和命令必须来自当前项目，不能为了填完整模板而编造。

Implementation note 和 Review rounds 用于后续记录实际执行与审查，不应提前填成“已通过”。预定验证与实际证据是不同内容，后者见[验证与反馈](07-verification-and-feedback.md)。

## 3. 从任务骨架到核实过的执行依据

当前 Plan 约定先发布执行细节的标题骨架，再由 Refine Ticket 核实并补齐内容。[1][3]两者的重点不同：前者确定交付和已决定的动作，后者确认执行这些动作需要的事实。

Refine Ticket 读取关联需求与设计、消费修订及相关代码，核对文件、符号、接口形态、测试入口和产物关系。它不能在事实缺失时猜一个值，也不能借细化任务重新选择方案。

五项执行细节分别要求：

| 小节 | 应当提供的内容 | 对导出任务的意义 |
|---|---|---|
| Verified contracts | 有文件、符号或依据链接支持的具体契约 | 请求者身份从哪里来，当前鉴权和查询接口怎样接收它 |
| Execution scenarios | 至少有成功与失败路径及可观察结果 | 权限允许时导出，权限被收回时按已定行为处理 |
| Expected tests | 可运行命令或具体用例，以及断言 | 检查结果范围和拒绝行为，而不只检查 CSV 能否生成 |
| Generated artifacts | 生产者、产物、消费者之间的同步要求；不适用时说明原因 | 核对任务涉及的生成关系，避免只改源定义而遗漏消费端 |
| Conventions | 局部非显然约定与转录的规范条款 | 提供本项目的错误表达、测试组织等适用要求 |

可执行任务需要具体的接口、代码位置和验证入口，这些信息应从当前仓库中核实。

如果接口不存在、契约相互矛盾，或者执行顺序仍未确定，细化环节应保留证据并返回相应的调查或设计工作。若任务已有失败记录，也应先处理其中的事实，把核实后的知识带入契约；未经验证的修复猜想不能写成确定答案。[3]

## 4. 项目规范如何成为任务中的适用条款

规范转录解决的是“当前任务具体应遵守哪些规则”。FlowForge 将识别、解释和转录分给不同环节，使执行者获得已经准备好的条款。[2][4]

```text
项目规范及提取指南
    ↓ Align：识别当前需求范围适用的规范
适用规范清单
    ↓ Design：写成明确条款并标注来源、归属
设计中的 Standards clauses
    ↓ Plan：按归属转录
任务中的 Constraints / Conventions
    ↓ Implement：检查准备状态并据此执行
```

例如，假设项目规范要求所有数据访问经过统一权限组件，设计应说明本次后台导出如何遵守它，并形成可引用的条款。Plan 按设计给定的归属，将硬性约束放进 Constraints，将相应约定放进 Conventions；不在转录时重新挑选规则或改写其含义。

这一链路不是简单复制规范全文。适用性和具体含义需要先明确，来源链接则供核对与追溯。如果设计缺少需要的规范条款，应返回补齐；如果已经判断没有适用规范，也要按约定表达这一结果，不能把未调查当作没有要求。

当前 CLI 只检查规范标记与状态，不解析条款是否准确覆盖项目规则。[6]因此，标记齐全只能说明满足相应的结构条件；选对规范和实际遵守规范，仍需要前序判断与后续审查。具体标记拼写应与当前契约及 CLI 接受的形式核对，不能仅凭近似表述假定检查等价。

## 5. 开工前检查哪些事情

任务准备完成后，Implement 仍需要核对有效规格、消费版本、诊断与执行契约。[5]这一检查把“文件已存在”和“当前可以执行”分开。

| 发现的问题 | 应采取的处理方向 |
|---|---|
| 前置任务尚未满足 | 先解决真实阻塞，不能只跳过依赖继续 |
| 上游依据已改变 | 对当前含义复核，确定任务是否仍适用 |
| 规范准备未完成 | 返回转录或相关设计环节，不让执行者临时重建规则 |
| 执行契约缺项或仍有占位内容 | 返回 Refine Ticket 核实补齐 |
| 动作包含未决需求或设计选择 | 返回负责该决定的环节，不能靠细化猜测答案 |

Catalog 对 schema 管理、处于可执行生命周期状态的任务检查执行细节：缺少必要章节或包含可识别的占位内容时，报告 `execution-contract-incomplete`。[6]Implement 约定这类缺口必须先解决，即使调用方选择在 frontier 中显示带 gap 的任务，也不能据此绕过该项开工检查。[5]

程序能识别部分结构缺失，但不能证明每条事实都准确、每个失败场景都充分。开工检查与事实核实共同工作，不能把“诊断消失”当成任务语义已经完整的证明。

## 6. 任务为主要入口，仍保留必要补读

准备好的任务应减少执行者反复搜索、解释需求和重新设计的负担。它需要承载本次交付的关键含义，同时提供代码与上游来源的明确入口。

当前执行约定仍要求读取项目不变量、关联需求设计和实际修改位置，遇到修订变化或代码与契约冲突时也需要核对。[5]这并不要求将全部项目文档重新读一遍，而是让必要阅读围绕当前工作展开。

任务内的信息也会过时。接口调整、前序任务修改实现，或者需求更新，都可能改变执行依据。因此，局部上下文需要可追溯、可复核；发现不一致时应明确返回，而不能把文档中的旧值强行实现到代码里。

任务准备由此形成一个交接结果：交付范围已定，局部依据可定位，动作和约束明确，执行事实已经核实，验证方式可用。下一步是结合依赖关系与当前诊断，确定这些任务如何推进。

## 仓库依据

1. [Plan](../../assets/skills/flowforge-plan/SKILL.md)：可验证增量、三层结构、骨架发布与规范转录。
2. [共享工件契约](../../assets/skills/_shared/ARTIFACT-CONTRACT.md)：局部信息、约束和执行记录的职责。
3. [Refine Ticket](../../assets/skills/flowforge-refine-ticket/SKILL.md)：事实核实、五项执行细节和失败知识的处理。
4. [Align](../../assets/skills/flowforge-align/SKILL.md) 与 [Solution Design](../../assets/skills/flowforge-solution-design/SKILL.md)：规范识别与条款形成。
5. [Implement](../../assets/skills/flowforge-implement/SKILL.md)：有效规格读取、开工检查与执行边界。
6. [Catalog](../../internal/tracker/catalog.go) 与[规范检查实现](../../internal/tracker/catalog_standards.go)：执行契约和规范标记检查范围。
