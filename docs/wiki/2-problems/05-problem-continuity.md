# 05. 多轮讨论后，需求与设计结论如何失去连续性

> 状态：正文初稿，供讨论完善。

需求分析结束时，用户认为关键边界已经讲清楚，Agent 也开始设计和拆分任务。但后续方案所依据的“需求”，是否仍然包含那些已确认的边界？

前面的[原理篇](../1-principles/03-agent-context-processing.md)解释了上下文如何保留、压缩和恢复。本篇关注它在工程协作中的一个具体后果：**人与 Agent 讨论形成的结论，没有完整、明确地成为后续工作的依据。**这种偏差可能沿着需求、设计、任务和验收逐步传递，直到交付时才被发现。

## 1. 讨论记录不直接等于当前结论

复杂需求是在讨论中逐渐确定的。同一句话在不同时间，可能有不同的地位：最初是建议，之后获得确认，再后来又因新的约束被替代。

例如，团队讨论一项数据导出功能：

| 讨论中的表述 | 当时的地位 | 后续应该如何理解 |
|---|---|---|
| “能不能直接提供全部字段的导出？” | 候选想法 | 需要分析，尚未承诺交付 |
| “导出范围应与用户当前能查看的数据一致。” | 已确认要求 | 设计必须满足的权限边界 |
| “第一期先支持 CSV，Excel 后续再做。” | 本期范围决定 | 当前交付不应自行扩展格式 |
| “下载链接有效期还没定。” | 未决问题 | 需要继续确认，不能当作已有答案 |

如果后续只是从历史中找到“导出全部字段”，却没有继承权限边界，就可能把候选想法当成最终要求。即使每句话都能找回，也仍需知道它是否被接受、适用于什么范围、是否已被替代。

因此，需要传递的是**当前有效结论及其状态**。哪些行为必须满足，哪些选择仍然开放，哪些旧想法已经退出方案，都要让后续工作能够辨认。否则，每次进入新阶段都需要重新解释讨论历史，已确认的决定也可能被重新猜测。

## 2. 一个遗漏如何传到设计、任务和验收

下面继续使用数据导出场景。它是说明问题的假设案例，不是实际项目事故记录。

用户在需求讨论中确认：导出应与页面查询遵守相同的数据权限。页面上不能查看的数据，也不能通过导出获得。讨论还涉及格式、字段顺序、文件大小和大数据量下的性能。

进入设计阶段时，整理出的需求却只写了：

> 支持按筛选条件导出 CSV；大数据量采用后台任务生成，完成后提供下载。

权限边界没有进入这份设计输入。后续可能沿着下面的路径推进：

| 阶段 | 基于当前输入作出的工作 | 偏差如何被带到下一步 |
|---|---|---|
| 需求整理 | 保留筛选、格式和性能要求 | 漏掉“与页面查询相同的数据权限” |
| 方案设计 | 选择后台生成文件，并按筛选条件查询数据 | 未明确后台任务如何携带和应用请求者的权限范围 |
| 任务规划 | 拆出任务提交、数据查询、文件生成和下载入口 | 没有任务要求核对页面与导出的权限一致性 |
| 实施 | 按设计接通后台查询与文件生成 | 功能可以运行，但可能导出请求者无权查看的数据 |
| 验证 | 检查字段、筛选、CSV 内容和大数据量处理 | 测试依据同样缺少跨权限范围的场景 |

此时，各环节可能都在认真执行收到的要求：设计符合整理后的需求，任务覆盖设计，代码完成任务，测试也通过。但最终交付仍然违背用户已经确认的权限边界。

**上游遗漏一旦成为下游共同使用的前提，局部一致性就可能掩盖整体偏差。**后续文档越完整、实现越具体，也不意味着最初丢失的要求会自动回来。

这个问题在设计结论的交接中同样存在。例如，设计讨论已经确定后台任务必须携带请求者的数据范围，拆任务时却只留下“实现后台查询”。执行者可能把遗漏的设计选择当成自由实现细节，再作出一个不同决定。

独立的权限测试、项目规范或审查可能发现这些问题。但如果实现与验收都依赖同一份不完整输入，就不能只凭二者一致，证明它们继承了用户的全部有效要求。

## 3. 为什么常见补救方式仍然留下缺口

### 保留完整聊天记录，还需要重新判断哪些内容有效

聊天记录能提供追溯材料，却往往按时间排列，混合了问题、建议、确认、修正和否定。接手者要恢复当前结论，仍需完成一次解释工作。

对于导出案例，需要找回的不只是一句权限要求，还包括它是否适用于后台导出、是否曾被明确调整。记录存在降低了无法追溯的风险，但不能代替当前结论的整理。

### 等到阶段结束再总结，可能把遗漏固定下来

阶段总结可以形成清晰入口，关键在于它依据什么编写、是否与已确认结论核对。如果总结时漏掉权限边界，接下来的设计和任务都可能把这份简洁文档当作完整依据。

文档因此产生了两种不同效果：它让已有内容更容易传递，也让未被发现的遗漏随之稳定传播。需要关注的不只是“有没有总结”，还包括结论何时得到记录，以及总结是否覆盖了会改变方案的条件。

### 让用户在后续不断纠偏，会把连续性维护转回用户

用户可能在看设计时再次提醒“导出不能越权”，但这要求用户记住之前说过什么，并逐层识别它有没有落实。遗漏还可能藏在接口、任务划分或测试场景中，不能只看功能介绍就发现。

纠偏越晚，受影响的下游工作可能越多：补一句需求，可能需要同时改变后台任务参数、查询接口、执行逻辑和测试。用户参与确认依然必要，但不能把反复重述已确认要求当作维持连续性的主要方式。

## 4. 需要解决的是：后续工作如何继承有效结论

这个问题要求协作过程能够回答四件事：

- **当前以什么为准？**已确认要求、已定设计、本期范围和未决问题有明确区别。
- **下一步继承了什么？**进入设计或任务规划时，能够核对关键边界是否被承接。
- **变化替代了什么？**新决定出现后，旧含义不再继续充当当前依据，受影响工作需要复核。
- **交付与什么比较？**验证能够回到有效要求，而不只检查代码是否完成了下游任务清单。

这也是 FlowForge 需要解决的第一个具体问题：**让多轮协作形成的有效结论持续成为下一步的工作依据，减少遗漏与误解沿阶段传播。**需求与设计如何持久维护、如何追踪变化，以及下游如何核对，将在[总体解法](../3-approach/10-approach-overview.md)和[需求与设计持久化](../4-features/12-authority-artifacts.md)中展开。

即使这些结论已经完整保存，执行者仍然要从需求、设计和规范中获得当前任务所需的信息。[第六篇](06-problem-retrieval.md)继续讨论这一环节：信息已经落盘，为什么仍然可能找不全或用错。
