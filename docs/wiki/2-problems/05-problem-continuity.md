# 05. 多轮讨论后，需求与设计结论如何失去连续性

> 状态：正文初稿，供讨论完善。

复杂需求很少在一次对话中确定。人与 Agent 需要反复确认目标、补充场景、比较方案，再根据反馈修正范围。讨论结束时，团队得到的不只是“要做某个功能”，还包括一组决定当前做法的信息：哪些要求已确认，哪些方案已排除，哪些边界不能改变，哪些问题仍未解决。

这些信息在讨论中连续出现，却不会自然地形成稳定、完整的后续输入。[前三篇原理](../1-principles/01-context-fundamentals.md)已经说明，历史需要经过保留、压缩、恢复和加载等过程才能进入后续 Context。对复杂工程而言，这带来一个具体问题：

> **后续阶段能否获得仍然有效的结论，并据此继续分析、设计和实施，而不依赖某次会话是否恰好记得早期讨论？**

本篇讨论这种连续性如何失效。信息已经正确落盘、但执行时没有准确取用，是下一篇要单独讨论的问题。

## 1. 需要连续传递的不只是需求条目

讨论产生的信息具有不同性质。如果全部混在一段历史中，后续读者很难判断哪些内容应当继续约束工作。

| 信息类型 | 例子 | 后续需要知道什么 |
|---|---|---|
| 已确认的需求 | 暂时性错误可以重试，永久性错误立即结束 | 这是当前应满足的行为，不是待选建议 |
| 范围与约束 | 本次保持旧配置兼容；不处理另一个发送渠道 | 哪些变化在本次范围内，哪些边界不能越过 |
| 已确认的设计 | 错误分类先于重试调度；幂等检查放在既定接口 | 后续实施不能把这些决定重新当成开放选择 |
| 被否定的方案与理由 | 不采用对所有异常统一重试，因为永久错误不能重试 | 避免再次提出同一方案；也避免把旧方案误当现行决定 |
| 尚未决定的问题 | 最大重试次数是否按渠道配置仍未确认 | 需要补齐或明确暂定范围，不能由执行者悄悄假设 |
| 环境与实现事实 | 当前错误类型不能区分永久与暂时失败 | 需要据此设计或调查，而不是把事实当作产品要求 |

这里至少有三类重要区别：**候选与确认、有效与失效、已解决与未解决。**它们发生变化时，文本可能仍然保留，信息在协作中的地位却已经不同。

例如，“所有异常统一重试”作为候选方案出现在讨论中是正常的。如果后来已明确否定，后续只看到这句话而没看到否定结论，就可能得到与讨论结果相反的理解。连续性不是完整复制每一句话，而是保留当前结论及其必要含义。

## 2. 连续性在哪些交接处容易断裂

复杂项目往往有多次信息转换，而不是只有“需求对话”和“编码”两个环节。

| 交接处 | 应当传递的有效信息 | 可能的失效表现 |
|---|---|---|
| 需求讨论继续深入 | 已确认目标、边界、范围及未决问题 | 新讨论推翻旧边界，却没有明确替代；重复询问已经确认的内容 |
| 需求进入设计 | 可观察行为、异常场景、外部约束和范围 | 设计只覆盖主流程，遗漏早期提出的失败或兼容场景 |
| 设计进入任务规划 | 已选责任、接口、顺序、验证策略和否决理由 | 拆任务时重新选择方案，或把未定接口写成实施指令 |
| 规划进入实施 | 当前任务所依据的有效要求与局部设计 | 执行者根据常见做法补全缺失信息，偏离已确认约定 |
| 修改或会话切换后继续 | 已更新的结论、实际工作状态和受影响范围 | 新会话沿用旧决定，或不知道哪些内容仍需复核 |

这些失效不一定都由上下文压缩造成。还可能是讨论中没有明确确认、决定没有落盘、更新没有传递到下游，或新材料根本没有被读取。第三篇已经给出相应的排查方向：只有观察实际输入、读取范围和会话状态，才能进一步区分原因。

因此，“已经讨论过”只能说明某个观点出现过，不能证明后续工作已经继承其当前含义。

## 3. 为什么阶段结束后补文档可能已经太晚

一种常见安排是：先充分讨论，等需求分析或方案设计结束时，再让 Agent 整理成文档。这种做法比完全没有文档好，但并不能自动消除早期信息已经不可用的问题。

### 整理工作依赖当时的可用信息

如果早期细节已经被省略、摘要中表达不完整，或者当前整理者并未参与原讨论，那么最终文档只能基于它现在能获得的信息编写。把已有内容写得更完整、更有条理，不等于恢复了遗漏的事实。

因此，总结文档的来源很重要：它是在结论确认时形成的，还是很久以后凭当前上下文补写的？两者的可靠性不能仅凭格式判断。

### 摘要可能改变条件的强度

原始讨论中的“只在暂时性错误下重试”，可能在总结中变成“支持失败重试”。前者有适用条件，后者是宽泛能力描述。摘要虽然保留了主题，却丢失了会改变实现的边界。

类似风险还包括把“待确认”写成“应该如此”，把“本次暂不处理”遗漏成没有范围限制，或把一次示例中的数字写成固定要求。

### 后续变更可能只改了当前环节

设计过程中发现旧方案不可行后，团队可能在设计文档里选择了新方案，却没有同步修改仍然引用旧方案的任务。如果只有“当前设计”而没有消费关系或复核过程，后续很难知道哪些工作受影响。

这说明持续维护不仅是保存第一次讨论结果，还包括让被替代的含义退出当前工作依据，并让受影响的下一步重新核对。

## 4. 一个连续性失效的例子

下面以消息重试为示意，展示同一项需求如何逐步偏离讨论结果。它不是实际会话记录，也不用于证明某种模型必然出现这些行为。

### 讨论中的有效结论

需求讨论确认了四件事：

1. 暂时性错误可以重试，永久性错误立即结束。
2. 重复请求不得造成重复发送。
3. 需要保持旧配置兼容。
4. “所有异常统一重试”的方案已被否定，因为它违反第一条。

设计讨论随后确定：先按错误契约分类，再进入重试调度；幂等检查在发送之前完成。最大重试次数的配置方式仍未确定。

### 信息开始失去连续性

一段时间后，当前交接材料只剩：

> 用户确认要支持消息失败重试；设计采用先分类后调度。下一步实现重试逻辑。

这份摘要保留了功能名称和部分设计，但遗漏了错误边界、幂等、兼容性以及未决配置问题。接手者可能产生几种不同的错误：

- 把已有异常处理接口直接包装成统一重试，重新采用已否定的方案；
- 实现次数限制和间隔，却遗漏重复请求场景；
- 为简化配置直接更换旧字段，破坏兼容要求；
- 自行决定最大次数按渠道配置，把未决问题当成既定设计。

如果只比较主题，交接材料并没有“忘记重试”；它遗漏的是决定正确行为的内容。后续测试若只覆盖一次暂时性失败后成功，也可能无法及时发现其他偏离。

### 文档存在也不一定意味着已经恢复

再假设早期讨论后来补写进了完整需求文档，但接手者没有读取它，只拿到了上面的摘要。这时问题已经从“结论没有保存”转成“保存后没有准确取用”。两种问题可能叠加，但不能因为最终仍有文档，就断定后续输入必然完整。

下一篇会专门分析这种“信息已经落盘，执行时仍然漏用”的情况。

## 5. 连续性失效会带来哪些工程后果

连续性不足通常不是立刻表现为明显的“记忆错误”，而是逐渐变成返工和难以核对的差异。

- **重复讨论：**已经确认的范围和约束被再次询问，协作成本增加。
- **隐性改需求：**缺少原始边界时，执行者按常见模式补齐，结果看似合理，实际改变了已确认行为。
- **重复或冲突的设计：**已否定方案再次出现，新旧决定同时存在，没人能确定当前依据。
- **未决问题被隐藏：**任务看起来可以直接执行，但其中包含尚未作出的需求或设计选择。
- **验收依据不完整：**实现只验证了保留下来的主路径，异常、兼容和权限等早期要求未进入验证。
- **错误定位困难：**最终交付偏离目标时，难以判断是讨论未确认、信息未保存、取用遗漏，还是已提供但未正确使用。

最后一点尤其重要。把所有偏差都归因于“模型上下文太短”，会掩盖需求本身未定、文档未更新和验证缺失等不同问题，也无法选择正确的修复方式。

## 6. 这个问题不等于什么

为了避免把问题说得过宽，需要保留几个边界。

- **不等于必须永久保留全部聊天记录。**许多探索过程不再约束当前工作，关键是有效结论及其必要依据能否恢复。
- **不等于长对话一定会丢失重要内容。**压缩和摘要可以支持长任务，具体保留效果取决于系统策略、信息性质和核对方式。
- **不等于写下一份文档就解决了问题。**文档也可能遗漏、过时或混淆候选与决定；写入后的加载和使用是后续问题。
- **不等于所有实现错误都来自连续性失效。**代码理解、模型能力、工具结果与验证范围仍可能影响结果。
- **不等于可以靠一次最终总结证明完整。**需要知道总结基于哪些有效信息，以及遗漏和变更如何被发现。

因此，连续性是一组可观察的信息管理问题，而不是“Agent 没有记忆”这一句概括。

## 7. 对后续方案提出了什么要求

从上述失效过程，可以先提出方案需要回答的问题，而不在这里预定具体功能：

1. 已确认的要求、设计、约束和未决问题，如何在讨论过程中形成可恢复的当前依据？
2. 候选、确认、替代和失效如何区分，避免后续误用历史观点？
3. 新阶段或新会话如何获得当前有效含义，而不是重新依赖完整对话记忆？
4. 结论变化后，如何识别并复核受影响的下游工作？
5. 如何核对后续交付确实继承了关键边界，而不只是保存了一份文档？

这些问题共同指向“结论需要及时沉淀并持续维护”。至于 FlowForge 如何通过需求与设计权威、修订和下游引用等机制回应，将在总体解法及功能篇展开。
