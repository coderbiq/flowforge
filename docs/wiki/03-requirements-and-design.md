# 03. 需求与设计管理：形成、维护与更新有效结论

> 状态：重组后的结构稿，正文待完善。

## 概要

围绕“后续工作以什么为准”，解释 FlowForge 如何接收材料、补齐依据、澄清需求、形成设计，并在结论改变时识别需要复核的下游。

## 正文规划

### 1. 从外部材料到待确认输入

说明 triage 与 import 如何区分来源事实、候选要求、设计决定、证据与冲突，保留出处而不把旧文档直接升级为现行要求。

### 2. 补事实与作决定分别由谁承担

归组说明研究、诊断、访谈、问卷、原型和决策地图如何支持当前未决问题；调查输出不能代替用户取舍或设计裁决。

### 3. 需求与设计为什么分开维护

解释两类权威各自负责什么、何时持续更新、未决问题如何限定影响范围，以及 compact ticket 的适用情况。

### 4. 引用与修订如何支持下游复核

解释语义链接、ID、revision、area 和 consumes；上游变化后由人和 Agent 判断含义影响，CLI 不自动更新下游正文。

### 5. 共享知识与局部上下文的边界

说明术语、ADR、可选规格导航与需求设计的区别；会话 handoff 指向执行协作篇，避免把临时进度变成长期设计。

## 内容边界

本文负责结论及其来源和变更；任务如何转录局部信息归入第04篇，版本诊断如何影响队列归入第05篇。

## 依据准备

核对 assets/skills 中 Align、Solution Design、Import 及辅助 Skill，共享工件契约与 internal/tracker/catalog_semantics.go。
