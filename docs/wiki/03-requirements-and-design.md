# 03. 需求与设计管理：形成、维护与更新有效结论

FlowForge 的需求与设计管理要解决一个具体问题：**后续工作以什么为准，怎样知道这个依据仍然有效？**为此，它把来源材料、待确认问题和已接受结论分开处理，再通过持续更新与引用修订支持交接。

## 1. 先辨认输入的性质，再决定它是否成为要求

需求可能来自用户对话，也可能从旧 PRD、历史提案、故障报告或代码现状开始。这些材料可以提供依据，但并非每句话都代表当前要实现的行为。

例如，一份旧导出方案里可能同时存在“暂时仅允许管理员使用”“后台直接查询数据库”和“测试环境生成文件成功”。它们分别可能是历史范围、旧设计与验证事实，不能一起转换成新任务的执行指令。

FlowForge 的 Import 约定先分类保留的信息，并为其保留文件和标题等来源定位。[1]

| 材料中的内容 | 如何进入后续工作 |
|---|---|
| 来源事实 | 作为理解当前行为或历史的依据，需要时核对现状 |
| 候选需求 | 交给需求澄清，确认目标、范围和行为是否仍成立 |
| 设计决定 | 交给方案设计，判断责任、接口和兼容选择是否适用 |
| 已交付或已验证的结果 | 保留为证据，不能自动变成未来要求 |
| 未知或冲突 | 指明影响的问题，由相应责任方解决 |

外部请求或 bug 还可以先经过 Triage，形成便于处理的简报；Import 负责已有材料的解释和分类。它们提供进入需求、设计工作的入口，不替代最终的含义确认。

这一安排使“文档里写过”与“当前已经接受”之间有明确的处理过程。来源可以追溯，当前结论则在负责该含义的位置维护。

## 2. 缺少事实与尚未决定，需要不同的处理方式

接收到输入后，Agent 首先要辨认当前缺口是什么。仓库能够回答的问题应先调查；影响业务结果的取舍需要确认；已确认要求如何落实则进入设计。[2][3]

继续使用后台导出案例：

| 当前问题 | 性质 | 处理方式 |
|---|---|---|
| 页面查询现在通过哪个组件过滤数据权限？ | 仓库事实 | 检查代码与现有约定，记录可核对的来源 |
| 用户提交导出后权限被收回，后台任务还能否导出？ | 需求选择 | 明确期望的业务行为与异常场景 |
| 后台任务怎样取得有效权限范围？ | 设计选择 | 基于已确认行为，决定接口、责任和信息流 |
| 某种方案在大数据量下是否可行？ | 待验证假设 | 用有界调查或原型获取证据，再回到设计比较 |

FlowForge 的研究、诊断、原型、访谈和问卷等辅助能力，围绕这些具体缺口使用。研究收集事实，诊断验证故障假设，原型检验难以在纸面上判断的行为；访谈和问卷用于获得责任方掌握的意图与取舍。大型工作还可以用决策地图组织尚未解决的问题。

这些活动的结果成为决定的输入。调查简报要区分事实与待裁决项，原型也不能仅因“跑得通”就自动成为生产设计。当前问题得到回答后，再回到需求或设计正文维护结论，避免让临时调查材料形成另一个相互竞争的依据。

## 3. 确认一项含义，就更新对应的当前正文

Align 负责确认可观察行为、范围、场景和约束；Solution Design 负责模块责任、接口、信息流、迁移与验证策略。区分两者，可以避免执行方便性悄悄改变用户期待，也可以避免把每个内部实现选择都重新交给需求讨论。[2][3]

在导出案例中，“权限应与页面一致”还需要澄清时间语义。假设用户确认：**后台任务执行时必须按用户当时的权限重新判断；权限已被收回时，不得导出相关数据。**这应进入需求正文。

设计随后需要确定任务保存哪些身份信息、谁负责重新鉴权、查询如何使用权限范围、失败怎样返回，以及用什么方式观察这些行为。这些是实现需求的决定，应进入设计正文。若设计只是把提交时的数据范围永久带入任务，就需要回到上述要求检查，而不能将技术选择当作已经满足了业务含义。

### 持续维护当前含义

两类 Skill 都要求在决定确认后更新对应权威，不等整个阶段结束再整理。已被替代的含义从当前正文中修正，语义发生变化时更新修订；格式调整不应被当作新的业务决定。[2][3]

设计还应保留有决策价值的替代方案理由。例如，为什么不采用提交时的权限快照，可能直接关系到后续兼容和安全边界。但无需把所有探索过程和未产生影响的讨论逐轮追加到正文。

小改动可以在一张紧凑任务里表达清楚；当需求或设计有多个消费者、独立评审或更长维护周期时，再提升为独立文档。划分依据是内容的使用方式，而不是要求每项需求都填满同一套模板。

### 未知项保持可见，并限定影响范围

如果下载链接有效期尚未确认，应明确它影响下载访问设计；不能随意写入一个默认天数，也不必因此认定所有导出工作都无法讨论。

FlowForge 用带解释位置与影响范围的未决项记录这类缺口。设计可以按语义区域组织，使已经解决的部分与仍待判断的部分区分开。具体工作是否能推进，还需要结合实际依赖与诊断判断，不能仅凭“这个问题属于另一节”认定互不影响。[3]

适用规范也在这一过程中进入设计：Align 识别当前范围适用的规范，Design 将其转成明确条款，后续再由 Plan 转录到任务。条款准备与执行检查将在[任务上下文](04-task-context.md)中展开。

## 4. 上游改变后，下游怎样知道需要复核

持久保存解决了“当前结论在哪里”的问题，还需要处理下游已经使用了旧结论的情况。FlowForge 把供人阅读的语义链接与供程序比较的修订记录结合使用。[4]

| 机制 | 用途 |
|---|---|
| 来源链接 | 让读者定位某项要求或设计的具体含义 |
| ID | 标识被引用的权威或语义区域 |
| revision | 表示其语义修订 |
| area | 在较大文档中标识可独立追踪的语义区域 |
| consumes | 记录下游已经审阅、采用的上游修订 |

这些机制不替代正文。元数据可以表明“任务使用了某设计区域的第2版”，但不能独自说明权限如何传递。

假设早期需求允许使用提交时的权限范围，后续用户改为执行时重新鉴权。更新需求含义及修订后，记录消费旧版需求的设计会出现版本落后提示。下一步应当是：

1. 复核具体变化，判断哪些设计决定受影响。
2. 修正相关接口、信息流与验证策略，并更新必要的设计修订。
3. 复核消费相关设计的任务，更新其执行依据与验证要求。
4. 已有实现和证据是否仍适用，也要按变更后的有效要求判断。

不能只把下游的消费数字改成最新版来消除提示。记录新修订，应意味着已经完成对当前含义的复核；是否无需修改，也应建立在这次判断之上。

当前 CLI 实现会对消费版本落后产生 warning，对缺失的权威产生 gap，也会检查机器引用与可读链接是否匹配。[5]它依赖正确维护的声明：如果含义改变却没有更新修订，或下游没有准确记录消费关系，不能期待版本比较自动发现全部影响。

CLI 也不自动比较业务语义、修改任务正文或完成所有下游修复。设计未更新前，其消费者未必立即呈现相同的版本变化。因此，这是一条由诊断提示、人与 Agent 复核、工件更新共同完成的过程；诊断如何影响队列见[依赖与推进](05-dependencies-and-progress.md)。

## 5. 共享知识、导航与历史分别放在哪里

为了让当前结论有明确位置，FlowForge 还区分了几种辅助文档的职责。[4][6]

| 内容 | 适合承载的位置 | 与需求、设计的关系 |
|---|---|---|
| 长期使用的领域术语 | `CONTEXT.md` 词汇表 | 统一语言，不承载功能规格和临时实现笔记 |
| 有长期影响的架构取舍 | ADR | 保留难以逆转、需要解释且有真实替代方案的决定；不为每个局部选择建一篇 |
| 多份依据的阅读入口 | 可选的 `spec.md` | 导航到需求、设计、任务和证据，不成为第二份权威正文 |
| 阶段活动记录 | proposal journal | 记录过程事件；当前需求与设计含义仍由正文维护 |
| 会话进度与恢复信息 | handoff 等交接材料 | 帮助恢复工作，不把临时状态变成长期设计 |

例如，删除一个可选导航文件，不应让原有需求、设计或依赖失去唯一依据。反过来，修改导航摘要也不能被视为已经修改了它链接的业务要求。

这些文档按需要建立。信息入口越多，维护成本也越高；只有内容有独立使用价值时，才值得新增一种保存位置。

## 6. 交给任务规划的应当是什么

经过上述过程，任务规划应获得当前有效的需求与设计、已核实的必要事实、适用约束，以及仍未解决问题的明确范围。它不应被迫从整段聊天里重新判定哪些话算数，也不应把缺少的设计选择直接转给执行者。

这套管理方式主要依赖 Skill 指导下的人与 Agent 持续维护内容，CLI 辅助核对声明关系。文档存在或检查通过，仍不能证明需求没有遗漏、设计一定正确。其价值在于让当前依据、未决问题和变更责任可见，便于后续执行与审查据此核对。
