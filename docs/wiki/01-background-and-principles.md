# 01. 背景与原理：复杂项目为什么需要精准上下文

FlowForge 的出发点是：复杂需求需要人与 Agent 经过多轮分析、设计和开发，而每一步能够可靠使用的信息有限。如何让当前工作获得充分、适用的上下文，并把有效结论传给下一步，是整套方案要解决的核心问题。

要理解这个问题，需要先区分信息保存、进入当前上下文和被正确使用这三个环节，再看它们如何影响工程协作。

## 1. Context：模型当前能够依据什么信息

模型训练中形成的知识、当前请求中的 Context，以及仓库或宿主保存的信息，承担不同职责。

| 层面 | 作用 | 不能据此假定什么 |
|---|---|---|
| 模型参数中的知识与能力 | 理解语言、编程概念和常见模式 | 不代表知道当前项目已确认的要求 |
| 当前 Context | 提供本次生成所依据的指令、消息、工具说明与材料 | 不代表已经包含项目中的全部相关信息 |
| 外部存储与会话状态 | 保存代码、文档、历史、证据等 | 文件存在不代表内容已被提供给当前生成 |

Context Window 通常以 token 表示一次请求的容量上限。Token 不等于字数；输入、输出、推理及多模态内容如何计入，需要按具体模型和 API 理解。[1][2]

Agent 执行任务时会经历多次生成：模型请求读取或采取行动，宿主或服务执行工具，再把结果组织进后续输入。[3]例如，需求文档里的权限条款，需要通过预先注入、读取或检索等路径进入当前工作，不能仅凭文件路径认为它已经被使用。

随着对话和工具结果累积，系统可能压缩历史、清理旧输出或限制读取范围。新会话和子代理也需要由宿主或调度者安排输入。具体策略有所不同，但都需要回答同一个问题：下一步实际获得了哪些信息？

## 2. 有效上下文：容量不等于使用能力

信息进入窗口后，还需要被定位、理解、组合并落实到行动。能够引用一条要求，不足以证明代码和验证已经满足它。

长上下文研究提供了相关证据：《Lost in the Middle》在其受测模型与任务中观察到信息位置影响表现；RULER 则显示，简单检索表现良好不能代表多步追踪、聚合等任务也同样可靠。[4][5]

这些结果有具体的模型、任务和年代范围，不能给当前所有模型划定统一的可靠长度。“有效上下文”指特定任务中可靠使用信息的能力与条件，不是另一个固定的 token 上限。

工程输入中的困难也不只有长度：旧方案与新方案混杂、适用范围不清、跨文档关系未说明，都可能增加判断负担。扩大窗口可以容纳更多材料，但不能替代这些问题的澄清。

## 3. 这些限制在复杂项目中表现为什么问题

复杂需求不是一次问答。讨论产生候选、确认、否定和未决内容，设计把要求转成责任与接口，任务再把设计变成实施动作。每次转换都需要传递当前有效含义。

| 具体困难 | 工程表现 |
|---|---|
| 结论没有稳定继承 | 早期确认的异常或兼容边界没有进入设计；旧方案再次被采用 |
| 信息保存了却难以取用 | 需求、设计和规范分散，执行者仍需查找、判断适用性并组合 |
| 任务缺少局部依据 | 任务只有名称或步骤，执行时还要补设计、猜接口和决定验收 |
| 交接缺少实际状态 | 新执行者不知道完成了什么、验证过什么、失败时尝试过什么 |
| 规范没有落实到具体工作 | 通用规范存在，但每次修改适用哪些条款仍需临场判断 |

这些困难可能来自记录、加载、更新或执行中的不同环节，不能统称为“模型忘了”。它们共同增加了后续工作重新寻找信息、解释历史和补全缺口的负担。

### 一个偏差沿阶段传播的例子

假设用户确认“数据导出必须遵守与页面查询相同的权限”，但阶段总结只保留了“按筛选条件后台生成 CSV”。设计可能没有安排后台任务携带请求者的权限范围，任务也没有要求核对权限一致性，测试则只检查格式、筛选和文件生成。

在这个假设案例中，设计、任务、代码和测试可以相互一致，交付却仍然违反用户确认的边界。上游遗漏成为下游共同前提后，仅检查局部一致性未必能够发现它。

保留聊天记录可以支持追溯，但仍需辨认候选与决定、有效与失效。阶段结束后再总结，也不能自然恢复当时已经不可用的细节。要求用户持续提醒，则把已确认信息的维护负担重新交还给用户。

## 4. 为什么只有文档或检索还不够

持久文件解决信息保存的一部分问题，检索提供取用路径；当前工作仍需要判断哪些内容适用、版本是否有效、还有哪些必要信息没找到。

同样，任务切小并不等于上下文充分。一个很短的“实现失败重试”任务，可能遗漏永久错误、幂等与兼容要求。反过来，把所有历史和项目规范都加载进来，也可能迫使执行者重新解释已经讨论过的决定。

因此需要区分几种准备方式：

- **全量加载相关材料：**适合规模可控或需要完整比较的工作，但仍需解释内容关系。
- **按需检索与读取：**适合动态仓库和探索，依赖可靠入口与补读，未命中不证明信息不存在。
- **摘要与压缩：**适合延续历史，但需要保留必要含义和来源，不能默认无损。
- **预先整理局部依据：**适合范围明确的工作，可以减少临场判断，但有准备与维护成本。

它们可以组合使用。Anthropic 的上下文工程文章也讨论了预先提供部分材料、再按需探索的混合方式，并提醒过度压缩可能遗漏关键细节。[6]

## 5. 精准上下文的目标与取舍

精准上下文的目标是：围绕当前工作提供充分、相关、来源与适用范围明确的信息，同时减少不必要的负担。它不以最短篇幅为目标，也不是现成的量化准确率指标。

分析需求需要场景、目标和未知项；设计需要有效要求、现有模块与约束；实施需要局部设计、代码坐标和验证方法；审查需要当前要求、变更与实际证据。每一步的信息需求不同，但以下条件应保持可核对：

1. 当前目标与范围明确。
2. 会改变做法的要求、约束和必要关系没有被省略。
3. 已定结论与待决问题分开，来源和适用版本可定位。
4. 缺少信息时有补充或返回路径，交付有验证依据。

更大窗口、更多 Agent 或更短任务都不能单独保证这些条件。准备、阅读、执行、审查与返工的成本应一起考虑，机制存在也不代表已经证明效果。

FlowForge 的整体设计将围绕这组要求展开：让有效结论离开临时对话得到持续维护，把当前工作需要的信息提前组织起来，并通过依赖计算和证据反馈支持逐步推进。具体分工见下一篇。
