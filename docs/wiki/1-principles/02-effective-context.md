# 02. 有效上下文：容量与可靠使用信息的能力

> 状态：正文初稿，供讨论完善。

[第一篇](01-context-fundamentals.md)说明了信息如何进入 Context。接下来还有一个问题：需求条款、设计和规范都已经读进来了，模型是否就能在当前任务中正确使用它们？

**Context Window 描述容量，任务表现体现信息是否被有效使用。**窗口扩大让系统能够提供更多材料，却不能单凭容量推导出模型可以准确处理其中的所有关系。找出一句话、判断这句话适用于哪个场景、再把它落实为代码，是不同的要求。

本 Wiki 用“有效上下文”讨论模型在特定任务中可靠使用所提供信息的能力及条件。这里不把它定义为模型固有的另一个固定 token 上限：它取决于模型、任务、输入组织和我们要求达到的正确程度。

## 1. 从“装得下”到“做得对”，还需要经过什么

以消息发送重试为例。需求规定“永久性错误立即结束”，设计规定先分类错误，再决定是否重试。模型拿到材料后，需要完成的不只是复述条款。

| 层面 | 当前要完成的事 | 可能出现的问题 |
|---|---|---|
| 容纳 | 把必要材料提供给本次生成，满足请求预算 | 材料未加载、被截断或已在摘要中遗漏 |
| 定位 | 从已提供的信息中找到相关条款 | 找到重试次数，却漏掉永久性错误边界 |
| 理解与组合 | 判断适用范围，结合设计与代码解释条款 | 将错误分类当成日志展示，未理解它应控制重试 |
| 应用与验证 | 在实现和验证中兑现要求 | 回答中提到了边界，代码却仍对全部错误重试 |

这四层是分析工作失败的视角，不代表模型内部存在四个独立运行的模块。

其中，材料根本没有进入本次输入，属于第一篇讨论的信息提供问题。材料仍然存在，却没有被正确定位、解释或落实，才是本篇重点。两者在聊天中都可能表现为“忘了”，需要通过读取结果、当前输入和实际交付区分原因。

同样，能准确引用一条要求，只能说明模型完成了这次引用。它并不充分证明后续设计、修改和测试都使用了这条要求。

## 2. 长上下文研究实际观察到了什么

### 信息位置会影响部分任务的表现

《Lost in the Middle》研究了多文档问答和键值检索任务，通过改变相关信息在输入中的位置观察模型表现。在其受测模型和设置中，相关信息位于开头或结尾时，表现往往较好；位于长输入中间时，表现可能明显下降。[1]

这个结果说明：内容进入窗口后，仍然可能因为组织位置不同而被使用得不一样。它为“容量与使用能力需要分开评估”提供了证据。

这项工作最初发表于 2023 年，不能直接作为当前所有模型的性能结论，也不能据此制定“只要放开头或结尾就一定可靠”的规则。实际效果还要看所用模型、材料与任务。

### 简单检索不能代表复杂信息处理

RULER 扩展了常见的“大海捞针”测试：除了寻找一条目标信息，还加入不同数量的目标、多步追踪与聚合等任务。在论文报告的受测模型中，许多模型在简单检索上接近满分，但随着长度和任务要求变化，其他任务的表现仍会下降。[2]

这与工程协作中的差别有关：“从文档里找出接口名称”与“同时满足权限、事务、兼容性和错误处理要求”需要不同程度的信息组合。后者即使每条信息都存在，也仍可能遗漏关系或适用条件。

RULER 还按其任务集合和评分阈值报告“有效上下文长度”。这个数值依赖测评定义，既不是模型的普遍硬上限，也不是生产任务的可靠性标准。作者也指出，测评与真实长上下文任务表现的相关性仍需验证。[2]

因此，论文中的结果不能换算成某个真实项目的成功率，也不能给今天的模型划定统一的有效长度。它支持的关键判断是：**评价长上下文能力，需要覆盖实际所需的信息处理方式，单项检索成绩不够。**

### 工程建议与原理证明需要区分

Anthropic 的上下文工程文章建议，为每一步选择能够支持目标的高价值信息，并关注长时间运行中的上下文管理。[3]这与上述研究共同支持一种工程方向：需要主动组织信息，而不能只增加输入量。

文章使用“注意力预算”等表述帮助解释问题。本文不把这类表述当作可逐 token 扣减的物理定律，也不据此断言“每增加一个 token，准确率就一定降低”。不同模型架构、训练和任务的表现需要具体研究；观察到遗漏，也不能仅凭结果确定它在模型内部的单一成因。

## 3. 什么会让已有信息难以被正确使用

在工程任务中，长度只是输入的一个特征。还需要检查内容本身及其组织关系。

| 因素 | 工程中的表现 | 增加的处理要求 |
|---|---|---|
| 相关信息分散 | 一个约束在需求中，另一个在设计附注，验证要求在任务末尾 | 找全并组合相关内容 |
| 相似内容干扰 | 多个模块都有重试规则，但适用范围不同 | 识别当前对象与规则边界 |
| 有效版本不明确 | 旧方案和新方案都出现在输入里，缺少明确状态 | 判断哪些内容已被替代 |
| 必要联系未写明 | 只列幂等要求和数据库接口，未说明它们在流程中的关系 | 补出本应已确定的设计含义 |
| 目标跨度过大 | 同一次工作同时分析需求、选择架构并改多个模块 | 维持更多尚未收敛的关系与约束 |
| 历史与输出冗余 | 大量无关日志、重复讨论与当前问题一起提供 | 从背景中筛选真正需要的事实 |

这些因素是工程分析维度，表中没有给它们分配固定的准确率影响。它们也不全是模型能力问题。例如，同一条规则有两个矛盾版本且未说明哪个有效，即使全部读懂，执行者也可能缺少作出正确选择的依据。

因此，上下文准备既包含减少阅读负担，也包含澄清信息的身份、范围和关系。标题、来源、适用场景与已确认状态能够帮助这项工作，但格式整齐本身不能保证含义完整。

## 4. 一个要求在三种上下文中的样子

继续使用消息重试场景。以下是解释信息组织差异的示例，没有声称对三组输入做过模型实验。

| 输入方式 | 交给 Agent 的内容 | 需要处理的困难 |
|---|---|---|
| 过少 | “实现消息失败重试” | 缺少错误分类、幂等、次数与验收边界，只能补问或猜测 |
| 全量堆入 | 完整历史讨论、多个版本设计、全项目规范与长日志 | 需要重新找出有效要求、判断适用规则、消解历史冲突 |
| 围绕当前任务组织 | 当前交付、相关需求边界、已定流程、代码坐标、适用规范和验证条件，附明确来源 | 可以围绕局部工作核对和实施；仍需验证内容充分且实现正确 |

第三种输入可以包含：

- 交付：为消息发送增加受控重试。
- 需求边界：暂时性错误进入重试；永久性错误立即结束；重复请求不得造成重复发送。
- 已定设计：先按既定契约分类错误，再决定是否调度重试；幂等检查的位置已经明确。
- 任务依据：错误分类、发送与调度相关代码位置，以及本次适用的规范。
- 验证：成功、暂时失败、永久失败和重复请求等场景的预期结果。

这只是内容轮廓，正式执行还需要具体接口、命令等事实。例子要说明的是：将分散信息组织到当前任务，不只是删减文字，还要保留决定行为的边界及其联系。

如果实际任务涉及旧配置迁移，输入中也必须包含兼容性信息。把它省掉虽然更短，却降低了信息充分性。必要材料有时需要增加，不能用字数减少代替上下文质量判断。

## 5. 怎样判断上下文是否有效

标称窗口大小可以从模型规格获取，而任务中的有效性需要通过使用结果判断。对复杂工程，更有用的问题包括：

- 能否识别当前任务适用的要求，并区分已失效或无关内容？
- 能否把跨文档约束落实到设计与实现，而不仅是复述？
- 能否处理成功路径和容易遗漏的异常、兼容性场景？
- 信息不足或存在冲突时，能否明确提出缺口并停止猜测？
- 在新会话中，仅凭准备好的材料是否仍能恢复同一工作范围？

评估时，可以用代表性任务对比不同材料组织方式，观察需求遗漏、错误应用、补读和返工，并结合实际验证判断。上下文消耗、准备成本与交付质量应一起考虑。

如果要研究长度本身的影响，应尽量保持模型、任务、关键事实与验证方法一致，分别变化长度、位置或干扰内容；否则，结果变化可能来自任务变难、事实被删除或提示被改写，不能全部归因于长度。

本文没有给出“超过多少 token 就不可靠”的统一数字，也不把一次成功执行当作稳定性证明。不同任务对正确程度的要求不同，同一个模型在简单查找和跨模块修改中的表现也需要分别验证。

## 6. 对 FlowForge 问题设定的启示

前面的原理与研究使我们能够提出更具体的上下文目标：当前步骤应当获得充分、相关、来源与适用范围明确的信息，并有办法验证这些信息确实被落实。

由此，FlowForge 需要处理的不只是“把需求保存下来”，还包括后续各步如何取用和组合有效结论。任务划分可以缩小一次工作范围，任务上下文可以组织局部依据，验证与审查则检查交付是否兑现要求。这些是需要进一步展开和检验的方案，研究本身并没有证明 FlowForge 已经取得相应效果。

扩大窗口、检索、摘要与任务准备都可能有价值，其适用性取决于工作需要。长材料中的必要信息要保留，缺失信息要补齐，冲突要澄清，无关负担才适合删减。第四篇将专门讨论这些取舍。
