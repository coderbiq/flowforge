# 04. 精准上下文：在相关、充分与有限之间取舍

> 状态：正文初稿，供讨论完善。

前三篇建立了三个认识：信息需要进入当前 Context 才能被使用；窗口容量不能保证使用效果；Agent 的读取、行动与交接会不断改变后续可用的信息。现在可以进一步讨论：每一步究竟应当提供哪些内容？

**精准上下文，是围绕当前工作，提供充分、相关、来源与适用范围明确的信息，并控制不必要的负担。**它既要避免遗漏关键条件，也要减少无关内容、过时版本与重复历史带来的判断成本。

这里的“精准”是一项工程目标。本文没有为整段 Context 定义可直接计算的精确率或召回率，也没有声称某种组织方式已取得特定成功率。以下方法用于组织和检查输入，实际效果仍需通过任务结果验证。

## 1. 先确定当前工作，再决定需要什么信息

同一项复杂需求，在不同步骤需要不同的信息。分析、设计、执行和审查都需要上下文，但它们要回答的问题并不相同。

| 当前工作 | 需要支持的判断 | 通常需要的信息 |
|---|---|---|
| 澄清需求 | 为什么做、哪些行为符合目标、范围在哪里 | 用户场景、现有行为、外部约束、已确认事实和待确认问题 |
| 设计方案 | 如何分配责任、安排接口和信息流 | 有效需求、现有模块与接口、适用规范、替代方案及验证依据 |
| 实施局部任务 | 在已定边界内完成具体交付 | 局部设计、需求边界、代码坐标、适用约束与验证方法 |
| 审查交付 | 实际结果是否符合有效约定 | 当前要求、固定范围的变更、验证证据与偏差处置 |

这张表不是要求各阶段只读某一类文档，而是说明信息应围绕当前判断选择。例如，实施时可能需要追溯某项设计理由，但通常不需要重新阅读所有被否定的候选方案。

因此，准备上下文的第一步是说明本次要完成什么、哪些决定已经确定、还有哪些问题需要判断。如果工作范围本身不清楚，就很难判断一份材料是必要依据还是无关背景。

## 2. 相关与充分需要同时满足

可以把选择信息时的风险分成两个方向：带入了不适用的内容，以及漏掉了本来需要的内容。它们不能只靠控制篇幅解决。

| 输入情况 | 可能造成的问题 | 准备时应关注什么 |
|---|---|---|
| 内容很少，但缺少异常场景或兼容要求 | 执行者需要补问，或按常见做法猜测 | 补齐会改变行为的条件 |
| 内容很多，混有历史方案和其他模块规则 | 执行者需要重新筛选、判断版本与范围 | 明确有效内容，分离无关历史 |
| 每条内容都相关，但联系没有写明 | 单条理解正确，组合后仍可能违反流程约束 | 保留接口、顺序和责任之间的关系 |
| 摘要简洁，但删掉了限制条件 | 形成表面合理、含义却已变化的输入 | 核对例外、否定条件和适用对象 |

例如，“失败后重试”与“仅对暂时性错误重试，永久性错误立即结束”都很短，但含义不同。若将后者压缩为前者，节省的文字恰好包含决定行为的边界。

Anthropic 的上下文工程文章提出，应寻找支持目标的高价值信息集合，同时提醒过度压缩可能丢失后来才显得关键的细节。[1]这支持一种准备顺序：先确认必要含义有没有保住，再消除重复和无关内容。不能以输入变短作为准备完成的依据。

## 3. 几种信息提供方式各自解决什么问题

全量加载、按需检索、摘要与预先整理都可能有用，它们处理的是不同的困难。

| 方式 | 适用情况 | 主要收益 | 需要承担的成本与风险 |
|---|---|---|---|
| 全量加载相关材料 | 材料规模可控，或需要完整比较、逐条核对 | 减少初次选择导致的遗漏 | 占用预算，仍需判断内容关系与适用性 |
| 按需检索与读取 | 仓库较大、内容变化快，下一步所需事实尚不明确 | 随工作进展获取具体内容 | 依赖检索入口、查询与补读，未命中不等于内容不存在 |
| 摘要与压缩 | 历史较长，需要延续目标、决定和工作状态 | 降低恢复与继续阅读的负担 | 需要核对摘要是否保留必要含义，并保留追溯来源 |
| 预先整理局部上下文 | 当前交付较明确，多种来源需要共同约束执行 | 提前组织局部依据，减少临场解释 | 有准备成本，上游变化后需要重新核对 |

实际工作可以采用组合方式：先提供任务目标、已确认约束和材料坐标，再读取当前代码；把大量日志保存在外部，先提供关键错误及定位信息，需要时继续查阅。

Anthropic 的文章也讨论了预先提供部分信息、再自主探索的混合方式，并指出合理的自主程度取决于任务。[1]这不意味着有一套适用于所有工作的固定比例。需求探索常需要更开放的阅读；范围明确的执行工作则更适合先组织好关键约束。

文件路径、标题和符号可以降低定位成本，但如果某条信息已知是当前执行必须遵守的条件，仅提供一个泛泛的目录链接，仍把适用性判断留给了执行者。相反，代码事实可能随修改变化，需要在行动时读取当前实现。如何安排，应按信息性质分别决定。

## 4. 怎样组织一份局部充分的上下文

“局部充分”指足以支持当前范围内的判断或执行，并且遇到缺口时有明确的补充路径。它不要求把整个项目复制进一份文档，也不能承诺执行者永远无需再读其他材料。

准备时可以依次回答以下问题：

1. **本次目标是什么？**写清可观察的交付或需要作出的决定，限定当前范围。
2. **哪些信息会改变做法？**保留需求边界、异常场景、兼容性和不能违反的约束。
3. **哪些决定已确定？**说明既定责任、接口和顺序，区分事实、方案与待决问题。
4. **依据在哪里，当前是否适用？**给出来源位置、适用范围及必要的版本信息。
5. **接下来如何行动和核对？**提供代码或材料坐标、验证方法，以及信息冲突时的返回路径。

其中第二项很重要：局部任务不仅有自身功能，也可能受跨模块条件约束。比如重试任务虽然集中在调度逻辑，却仍需保留幂等和旧配置兼容要求。任务范围小，不能成为删除这些边界的理由。

这组问题也是准备者的检查方法，不意味着所有任务都要套用相同标题。简单工作可能几段话就足够；更复杂的工作需要明确的信息来源和独立核对。

## 5. 从重试任务看信息选择

假设当前工作已经从方案设计进入实施，要在既定发送流程中加入受控重试。准备上下文时，可以分别处理不同材料。

| 来源材料 | 当前需要保留或提供什么 | 其余内容如何安排 |
|---|---|---|
| 需求讨论 | 暂时错误重试、永久错误结束、重复请求不得重复发送等已确认行为 | 历史提问与已替代想法留在历史中，当前结论有持久来源 |
| 设计方案 | 已选流程、分类与调度的职责、关键接口和顺序 | 未采用方案按需追溯；仍决定当前约束的理由保留 |
| 项目规范 | 本次适用的错误处理、分层或测试条款及来源 | 无关模块规则不必一起带入 |
| 当前代码 | 修改位置与相关契约；执行时读取实际实现 | 全仓库代码保留在外部，通过明确坐标逐步访问 |
| 验证与失败记录 | 本次要验证的场景，以及仍影响执行的已知失败事实 | 大量原始输出可另存，提供必要结果与定位入口 |

组织后的输入应使执行者知道：本次交付什么，哪些行为必须保留，设计中哪些内容不能自行改选，应该读取哪里，以及怎样证明完成。

如果准备过程中发现“永久错误如何分类”仍未决定，就应把它明确为待解决问题，而不是写进摘要后让执行者自行补全。同样，如果实现与设计不一致，需要核对事实或返回相应决定环节，不能靠更精简的文字掩盖缺口。

这个例子是信息组织示意，没有对其执行成功率进行测量。后续功能篇将介绍 FlowForge 如何用工件、任务契约和检查机制承载这些信息。

## 6. 上下文质量还需要通过工作结果检验

一次准备完成后，可以先检查关键要求、适用规则、来源和验证入口是否覆盖当前工作。但这些检查只能发现部分缺口，不能证明交付必然正确。

更有用的反馈来自实际推进：执行者是否反复补问已确认的要求，是否误用旧方案，是否因缺少事实被迫停下，审查是否发现本可提前提供的边界被遗漏。发生这些情况后，应判断是原始要求未定、准备遗漏、材料过时，还是已提供的信息没有被正确使用。

成本也需要完整计算。预先整理需要时间，检索可能需要多轮调用，摘要需要生成和核对，局部副本需要维护。应结合准备、阅读、执行、审查与返工评价整体效果，不能只看输入 token 减少了多少。

因此，本文给出的是可检验的方向：在必要含义完整、来源适用和能够验证的前提下，减少不必要的阅读与推断。它不支持固定字数目标，也不证明某种模板已经比其他方式更有效。

## 7. 从原理进入 FlowForge 的具体问题

至此，原理部分可以归结为一条工作要求：复杂需求需要持续形成有效结论，再把其中与当前步骤有关的充分信息交给 Agent，并根据实际反馈核对与更新。

这涉及的困难已经超出了单次提示词写法。多轮讨论中的结论怎样保存，文档中的信息怎样准确取用，任务如何具备执行依据，交接怎样保留实际状态，项目规范怎样适用于每次修改，都需要在协作流程中分别解决。
