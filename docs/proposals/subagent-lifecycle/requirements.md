# Subagent 生命周期管理需求

## 问题

FlowForge 用 `flowforge-*` Skill 承载工程方法论，并通过 `init`/`upgrade` 把 Skill 与 agent 规则文档确定性地部署到项目中。但"子代理"（subagent：角色职责 + 对 Skill 的规范化调用绑定 + 指定模型）目前没有对等的一等公民地位：仓库里只有 `.codex/agents/*.toml` 这一套历史原型，格式与 Codex 宿主强耦合，既不能被 opencode、Claude Code 识别，也未纳入 CLI 的部署/校验管线（对照 `docs/research/2026-08-29-subagent-design-reference.md` 的调研结论：Markdown + frontmatter 是宿主类项目的事实标准定义形态，且部署与撤销都应是确定性的文件操作）。

用户需要新增子代理能力：既要能使用 FlowForge 内置提供的默认角色（类比现有内置 Skill），也要能在项目中新增自定义子代理；子代理定义要能被 opencode、Claude Code、Codex 三个宿主同时识别和调用；并需要 CLI 命令管理子代理在这些宿主中的生效与移除。

## 目标

1. 用户可以为一个子代理编写一份权威定义（角色职责、对 Skill 的调用绑定、使用的模型），并通过 FlowForge CLI 把它变为 opencode、Claude Code、Codex 三个宿主都能发现和调用的原生子代理文件。
2. FlowForge 随发行版内置至少一套默认的 `flowforge-*` 子代理角色，未经用户任何自定义即可随 `init`/`upgrade` 一起可用，与内置 Skill 的分发方式一致。
3. 用户可以在内置角色之外，为项目新增自定义子代理定义，并让它进入与内置角色相同的部署/移除生命周期。
4. `flowforge agents` 提供部署与移除两个动作：
   - 部署：把一个子代理的权威定义编译为 opencode、Claude Code、Codex 的宿主原生格式，写入各宿主的原生子代理目录，使该子代理在对应宿主中可被发现和调用。部署是确定性的文件生成操作，不拉起、不管理任何 LLM 会话或进程。
   - 移除：撤销该子代理在已部署宿主目录中的原生文件，**并删除该子代理的权威定义源文件本身**——移除后再次部署不会让该子代理在任何宿主中重新出现，除非重新创建权威定义。
5. 用户可以确定性地核对某个子代理在三个宿主中的部署状态（一致 / 缺失 / 内容漂移），复用现有受管资源比对（`assets compare`/`verify`）已建立的语义。

## 范围与约束

- 本轮仅覆盖三个宿主：opencode、Claude Code、Codex。不新增其他宿主适配。
- "部署"和"移除"只是确定性文件生成与清理，不涉及启动/终止任何代理会话、进程或网络请求。
- 移除操作会删除权威定义源文件，是真实的"卸载"动作，而不是仅切换某个开关；具体的安全确认路径（例如是否需要显式确认、是否允许仅撤销宿主部署而保留定义的中间态）留给 Solution Design 设计。
- 内置 `flowforge-*` 子代理与用户自定义子代理共享同一套部署/移除生命周期命令；如何在共享生命周期下区分、标记或保护内置角色不被误删，留给 Solution Design。
- 子代理权威定义的具体字段集合（角色职责表达方式、Skill 调用绑定的语法、模型字段取值规则）、默认内置角色列表及职责划分、各宿主的编译规则细节，均由 Solution Design 决定，不在本需求中固定。
- 子代理与现有 Skill 体系的调用关系（子代理是否必须绑定固定 Skill、是否允许运行时调用清单外 Skill）由 Solution Design 决定。
- 委派/编排逻辑（谁做协调者、委派深度、结果契约）不在本需求范围，属于后续设计或功能。

## 可观察验收

- 给定一份子代理权威定义（内置或用户自定义），执行部署命令后，opencode、Claude Code、Codex 三个宿主的原生子代理目录中都出现可被各自宿主发现和调用的对应文件。
- 执行移除命令后，该子代理在此前已部署的全部宿主目录中的原生文件被删除，其权威定义源文件也被删除；再次执行部署不会让该子代理在任何宿主中重新出现。
- 全新安装或升级后（未做任何自定义），项目中已存在非空的默认 `flowforge-*` 子代理集合，且这些角色已按上一条验收标准部署到三个宿主。
- 用户新增一个自定义子代理定义后，无需修改内置角色即可通过同一部署命令使其在三个宿主中生效，并可通过同一移除命令卸载。
- 存在一种核对方式，能对每个已知子代理逐宿主报告当前状态为一致、缺失或漂移，且能把项目自有的额外宿主文件与受管子代理区分开。

## 非目标

- 不在本需求中确定子代理定义文件的具体字段 schema、格式或 Skill 绑定语法——这些是 Solution Design 的职责。
- 不实现协调者角色、委派路由、结果契约或多智能体编排逻辑。
- 不支持 opencode、Claude Code、Codex 以外的宿主。
- 不构建管理实时 LLM 会话或进程的能力；"部署/移除"严格限定为确定性文件生命周期操作。
