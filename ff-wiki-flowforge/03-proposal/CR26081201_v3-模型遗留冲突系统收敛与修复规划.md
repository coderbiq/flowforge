## Architecture Overview

### 事实分层

1. Markdown/frontmatter 与配置是事实源；SQLite `card_index`、links、tags、terms 是可重建派生索引，不是迁移授权。
2. 当前 v3 runtime card domain 应由 `PROP/FEATURE` 及其阶段、History、Journal 组成；横切知识使用 `CONV/DEC/MOD/FIND`。旧卡直接忽略，旧 task/design/log/structure/requirement CLI 直接删除废弃；旧 ID 与 links 不修改、不 alias。`STR-<proposal>-REQ` 是例外的 FlowForge 内部 Proposal control-plane metadata，不是 runtime card domain 成员：CreateProposal 继续创建/维护，Proposal inspect/FEATURE traceability 由独立 metadata domain loader 读取；普通 CardStore read/list/search/index 与 SQLite 派生索引不得读取或收录 STR。
3. 历史 wiki、当前 v3 workspace、library 和 proposal 路径仍可能被 Store 查找/fallback 交叉消费；本次不迁移、不展示、不搜索、不处理历史数据，未来迁移必须另立 Proposal。
4. assets 是部署边界：只更新 FlowForge 管理区块；用户自定义内容、checksum 漂移和非管理文件必须报告 conflict/preserved，不得无条件覆盖。

### 依赖顺序

`DEC 已决策 → 运行时拒绝/忽略边界（含 runtime card domain / proposal metadata domain 分离）→ CardType/ID/store/links 核心收敛 → CLI/batch/library → 当前文档契约 → assets 管理区同步`；UI、历史 wiki 和迁移不在本次链路。方案 A 的 control-plane metadata loader 是运行时 Step 1 的前置收敛点，核心 FEATURE Step 1 必须等待其完成并通过验证。

该顺序是已批准的设计边界；本次实现仍由后续 Executor 执行，历史文件、旧 ID/links 和 wiki 数据不作任何写入、改名、移动、删除或重写。
