# batch 部分失败采用报告式部分成功

## Context

batch 当前采用两阶段处理：先分配 ID 并写入卡片，再解析 `@ref`、校验 link target、写回 links/navigation。现有实现已经可能在第二阶段失败时留下第一阶段的卡片和已推进的 sequence counter；既有证据不足以推出事务回滚语义。该决策只收敛本 Proposal 的产品行为，不增加 CLI 参数或命令签名。

## Decision

用户明确选择 B：batch 部分失败采用“报告式部分成功”。

1. 已成功写入的卡片保留；任何已经发生的 links、navigation 和 sequence counter 写入也保留。失败项不做删除、反向 link、navigation 恢复或 sequence counter 回拨。
2. Phase 1 创建失败的条目不冒充成功；同批其他成功条目继续保留。Phase 2 的 bad ref、缺失 target 或 links/navigation 写回失败必须按条目报告，不能把此前已完成的写入伪装为整体失败后回滚。
3. 失败报告必须稳定、明确、可审计：保留现有 batch 结果中的成功项 `ID/type/title` 与失败项 manifest index/error；错误文本必须能区分创建阶段与 link/ref 阶段，并包含原始条目索引及可定位的 ID、ref 或 target（若已分配）。不新增 CLI 参数或命令签名。
4. duplicate ID 必须拒绝冲突写入并报告对应条目；不得覆盖已有卡。duplicate `ref` 仍属于 manifest 校验错误，在 Phase 1 前失败；未解析的 `@ref`、不存在的 target 属于 Phase 2 条目错误，已写入内容保留。
5. sequence counter 严格按现有 `NextCardID` 可观察行为验证：ID 分配成功后即保留 counter 的前移，任何后续创建或 link/ref 失败都不得回拨或伪造事务恢复；测试必须以真实 counter 文件和后续 ID 分配证明单调、不碰撞，而不是引入新的事务语义。
6. 重复扫描继续由 Step 2 的物理路径去重入口负责；batch 的 link/ref 解析与 library suggest/list 不得因同一物理卡重复扫描而产生重复结果或重复副作用。
7. library 只处理已确认的 current-v3 横切知识边界 `CONV/DEC/MOD/FIND`；`PROP/FEATURE` workspace/proposal 卡、legacy 卡和 STR control-plane metadata 不得被 import/promote/suggest/list 当作 library 卡或候选项。越界输入明确拒绝，现有合法 library 卡及其 links 保留。

## Rationale

该选择与当前两阶段实现事实一致，避免在未实现事务日志、补偿删除或 counter 恢复机制的情况下虚构原子性；同时通过稳定的逐条报告让调用方知道哪些写入已保留、哪些条目失败。它也保持 v3 的数据保护边界：不改写历史卡、旧 ID/links、STR metadata 或历史 wiki。

## Consequences

Executor 必须覆盖 phase 1/phase 2 的成功与失败组合，并验证已写卡、links/navigation 和 sequence counter 的保留状态。输出回归测试必须锁定成功项列表、失败项索引与阶段/对象定位信息。该决策不授权新增 CLI 签名，也不授权迁移、删除或回滚历史数据。

## Alternatives

未选择事务式回滚；本次不实现跨卡 rollback、link/navigation 补偿或 sequence counter 恢复。若未来需要原子批处理，必须另立 DEC/FEATURE，先设计可验证的事务或补偿机制。
