# 运行时 v2 残留与历史解析边界证据

## Summary

为 `W1-runtime-symbols` 提供运行时符号、调用链和历史解析责任的可复查证据。

## Source

仓库内只读证据（无外部来源）：`internal/core/card.go:13-106`、`naming.go:27-66,153-213`、`card_sequence.go:17-38,116-137`、`store.go:169-218,291-307,437-514,557-599`、`validate.go:43-58,180-203,249-312`；`internal/state/sync.go:21-86,225-334`、`index.go:21-94`；`internal/command/root.go:41-59`、`card.go:150-207`、`task.go:14-30,36-85,119-180,316-472`、`log.go:35-75`、`structure.go:13-25`、`migrate.go:11-39`、`upgrade_migrate.go:81-159`、`card_evolve.go:14-165,278-359`、`proposal_report.go:120-150,552-610,729-787,891-976,1480-1580`。测试证据为 `internal/core/naming_test.go:29-104,226-322`、`card_test.go:10-54`、`internal/command/proposal_test.go:314-335`、`project_test.go:301-303`、`runtime_v3_test.go:65-159`。契约对照 `docs/proposal-v3/card-model.md:9-30`、`docs/proposal-v3/cli-spec.md` 与 CR26081201 的运行时 FEATURE/FIND。只读仓库来源，不访问外部资料。

## Evidence

### 1. CardType、Prefix、前缀解析

- **Fact — current/legacy 分层**：`CardType.Valid()` 委托 `IsCurrentType()`；current 仅 DEC/CONV/FIND/MOD/PROP/FEAT（`card.go:29-41`），REQ/DES/TASK/LOG/STR 被 `IsLegacyType()` 单独识别（`card.go:43-50`）。旧常量、`Prefix()`、`CardTypeFromPrefix()` 仍是核心 API（`card.go:15-27,53-106`）。
- **Fact — current 写入依赖 Prefix**：`GenerateCardID` 和提案序号 `NextCardID` 使用 `Prefix()`（`naming.go:27-38`; `card_sequence.go:19-31`）；`card create` 先 `ct.Valid()` 再分配 ID（`command/card.go:171-207`）。Prefix 不能整体删除，旧分支可从 current 写入 API 中移除，但需先处理历史常量的解析/校验责任。
- **Fact — 旧 actionable 实现仍在源码**：`task.go:14-30`、`log.go:35-75`、`structure.go:13-25` 仍提供旧命令实现；`card.go:155-156` 帮助文本仍列 requirement/structure，但 `card.go:171-174` 由 Valid 层拒绝旧类型。`store.go:61-89` 仍保留 REQ/DES/TASK/LOG/STR 目录映射。
- **Fact — 历史扫描与 current 查询分开**：`ListCardsFromFiles` 解析 frontmatter 后仅收集 `IsCurrentType()`（`store.go:557-585`）；`ReadCard`/`FindCardPath` 对旧前缀直接 not-found（`store.go:291-307,437-471`）。旧文件因此可被扫描/解析后过滤，但不进入 current 查询。
- **Interpretation — 处置**：current-v3 可删除旧类型的创建/命令/库目录分支；`IsLegacyType`、旧 Prefix 映射及最小 frontmatter 解析责任在历史隔离方案明确前只能保留或收窄为内部 legacy-read boundary。不能把 STR 映射删除后再声称 Proposal metadata 可用。

### 2. ParseCardID、GenerateTaskID、Task-specific

- **Fact — `GenerateTaskID` 无生产调用者**：精确调用命中仅 `internal/core/naming_test.go:54-71`、`internal/command/proposal_test.go:315,331`、`internal/command/project_test.go:302`；生产代码无 `GenerateTaskID(`。`NextTaskID` 已返回 `task card IDs are not supported`（`card_sequence.go:34-38`）。
- **Fact — `ParseCardID` 无生产调用者**：精确调用命中仅 `internal/core/naming_test.go:226-270`；当前文件定位使用 `ParseFilename` 和 ID/PROP fallback（`store.go:437-514`），不是 `ParseCardID`。实现仍保留普通 ID 与 TASK 特殊四/五段形状（`naming.go:164-195`）。
- **Fact — task-specific 仍是旧簇**：`validateCardID` 对 TASK 检查段数和 task letter（`validate.go:180-203`）；`task.go:472-522` 有 task type/template；`GenerateSubTaskID`/`GetParentTaskID` 在 `naming.go:51-66,198-213`；Proposal report 在 `proposal_report.go:891-976` 处理 TASK/subtask 关系。
- **Interpretation — 处置**：`GenerateTaskID` 与 `ParseCardID` 是强删除候选（仓库内无生产调用；删除会影响命名测试和旧测试 fixture）。`GenerateSubTaskID`、`GetParentTaskID`、task-specific 校验/报告属于旧 TASK 命令/报告簇，应整体审查，不能只删生成器留下半可用 TASK API。
- **Risk**：旧 TASK 文件的 ID/links 不能因删除生成器而改写；未来定位/迁移须另立 Proposal，保留原字节、路径和 links。

### 3. validate / card_evolve

- **Fact — current 校验**：`ValidateCard` 在 `card.Type.Valid()` 失败时报告 invalid type（`validate.go:43-58`）；`ValidateCardFileInStore` 仍有 STR-REQ 结构索引特殊校验（`validate.go:295-307`），普通 links 通过 `store.ReadCard` 校验（`validate.go:267-279`）。
- **Fact — STR control-plane 例外**：`CreateProposal` 必然写 `STR-{proposal}-REQ`（`store.go:169-218`）；Proposal report 的 metadata/health 路径显式识别 STR（`proposal_report.go:120-150,1480-1580`）。STR 不能作为普通 Card 域保留，但 control-plane 生成/独立读取责任必须保留；删除 `CardTypeStructure` 或 STR 分支前必须先分离 metadata loader 与普通 Card 校验。
- **Fact — `card_evolve` 主体是 current FEATURE 契约**：命令只接受 FEATURE（`card_evolve.go:35-64`），阶段/复杂分析门禁在 `card_evolve.go:87-165`，测试覆盖其 gate（`card_evolve_test.go:13-69`）；这些不是旧 TASK 逻辑，应保留。
- **Fact — legacy cross-reference 残留**：`crossRefRe` 匹配 DES/REQ/TASK/STR（`card_evolve.go:278-283`），planned gate 命中即报错（`card_evolve.go:339-359`）。它是 current FEATURE 对旧引用的拒绝规则，不是历史读取；可标记为 legacy-reference policy，是否删除旧前缀分支需后续契约决定。
- **Fact — upgrade/migrate 独立**：`upgrade_migrate.go:81-159` 只搬移旧 workspace 目录并更新 PROP 状态，无 `ParseCardID`/`GenerateTaskID` 调用；但会移动文件/删除空目录，需迁移专题单独复核。

### 4. state / 查询与索引

- **Fact**：`RebuildDerivedIndex` 仅写入 `card.Type.IsCurrentType()`（`state/index.go:63-86`）；sync 的 `ReadCard`/`FindCardPath` 对 REQ/DES/TASK/LOG/STR 返回 not-found（`state/sync.go:225-263,323-334`），文件扫描同样过滤 current（`state/sync.go:315-320`）。这支持旧卡不进入 current 查询/索引，不支持删除历史文件。
- **Interpretation**：`legacyID`/`legacyCardID` 是 current read boundary 而非历史解析器，应保留至历史隔离策略落地；索引依赖 `IsCurrentType`，删除旧常量前需同步处理旧目录、报告和测试引用。
