# FlowForge

FlowForge 是一套与 AI Agent 协作开发的工作流。它把需求、设计、任务和验证结果保存在项目里，为每一步工作准备需要的上下文，让复杂需求能够经过多轮讨论、实施和审查逐步完成。Skill 指导 Agent 如何开展工作，Markdown 保存结论，CLI 检查依赖和任务状态。你通过对话提出目标、确认方案、推动进展，Agent 在背后使用这些工具，把工作持续推进下去。

支持 Claude Code、OpenCode、Codex 和 PI。设计原理见 [FlowForge Wiki](docs/wiki/README.md)。

## 快速开始

### 先为项目准备 FlowForge

在你使用的 Agent 工具中打开项目，然后告诉它：

> 帮我在这个项目中安装和配置 FlowForge，项目地址是 https://github.com/coderbiq/flowforge 。

Agent 会检查已有配置，安装 FlowForge，准备工程 Skill 和当前工具使用的子代理角色，并建立保存项目文档的目录。它还需要核对当前环境是否能够使用这些角色；例如 PI 的子代理能力需要相应扩展。安装依据见[发布页](https://github.com/coderbiq/flowforge/releases/latest)、[安装脚本](scripts/install.sh)（[Windows](scripts/install.ps1)）和[配置说明](docs/cli-design.md)。需要登录、授权或重新加载会话时，按 Agent 给出的提示操作。

接着，让它了解项目的规则：

> 根据这个项目已有的架构、开发和测试规范，完善 FlowForge 的项目规范说明。

FlowForge 提供通用的规范提取指南。Agent 会结合项目实际文档完善这份指南，让后续需求分析知道应该查哪些规范，并把适用规则带入设计和任务。已有约定直接采用，缺少的约定再与你讨论。

项目准备完成后，就可以开始第一个 proposal。

## 从一个 proposal 开始

**Proposal 是围绕一项需求或问题组织起来的一组工作。**它将需求、设计、执行任务和交付证据放在一起，方便持续讨论，也方便换一个会话继续。下面以“数据导出”为例，走一遍实际使用过程。

### 1. 启动流程，创建 proposal

> 启动 FlowForge 流程，创建一个新的 proposal：数据导出。我要让用户导出当前查询结果，权限范围和页面查询保持一致。先来分析需求和设计方案。

Agent 会先调查现有查询、权限和导出代码，再找出需要你决定的问题。例如：用户提交导出后权限被收回，后台任务应该使用提交时还是执行时的权限？这种问题会影响用户看到的结果，需要在需求阶段说清楚。

FlowForge 的需求澄清流程（Align）负责整理目标、范围、场景和约束。确认一项结论，就更新到 proposal 中；尚未决定的问题单独保留，说明它影响哪部分工作。如果你提供旧 PRD 或历史方案，材料导入流程（Import）会先区分仍有效的要求、旧设计和已验证事实，再交给需求或设计环节处理。

**这一轮你会看到：**需求文档、需要确认的问题，以及接下来要讨论的设计内容。文档默认位于 `ff-wiki/proposals/` 下，具体路径由 Agent 返回。

### 2. 讨论方案，保存确认的设计

你可以直接回应 Agent 的问题，或者纠正它的理解：

> 权限要在后台执行时重新判断。基于这个要求继续设计，看看现有的权限模块能不能复用。

方案设计流程（Solution Design）会依据已确认的需求，确定哪些模块负责什么、接口怎样衔接、数据如何流转，以及如何验证结果。项目中适用的规范也会在这一阶段变成明确的设计约束。

你可以多轮讨论方案。每次确认后，Agent 都应更新设计文档；如果讨论改变了需求，则同步修正需求及受影响的设计，避免后续任务继续采用旧结论。

认可方案时，可以说：

> 同意，继续推进，先把设计落盘。

**这一轮你会看到：**当前方案、关键取舍及理由、验证思路，以及尚未解决的问题。确认的结论保存在 proposal 中，后续实施可以直接追溯。

### 3. 将方案拆成可执行任务

> 按确认的方案拆分任务，说明每张票要交付什么。

任务规划流程（Plan）会把方案拆成能够分别实现和验证的小任务。每张任务票写明交付结果、修改位置、具体动作、允许修改的范围和验证方法，并链接到相关需求与设计。任务细化流程（Refine Ticket）再核实接口、代码位置和测试入口，让执行者知道从哪里改、怎样判断做完了。

FlowForge 同时记录真实的前置依赖。例如，接入后台导出的任务如果需要一个尚未实现的权限接口，就必须等接口任务完成。Agent 会调用工具检查这些关系，列出当前可以执行的任务和仍然受阻的任务。

**这一轮你会看到：**任务列表、交付顺序和阻塞原因。若任务名称或拆分方式看不懂，可以直接问：

> 不太看得明白这些票在做什么，解释一下每张票要交付什么，为什么要这样拆。

小改动可以用一张任务票承载需求、设计和验证，不必为每项工作建立一整套独立文档。

### 4. 开始实施，持续推进

> 开始实施这个 proposal。

实施流程（Implement）会检查任务需要的信息是否齐全、前面的任务是否已经完成，再安排当前可以做的工作。每张任务由新的 Agent 会话或子代理执行，读取相关需求、设计和代码，在约定范围内修改并运行验证。哪些任务可以同时进行，还要检查它们是否会修改同一文件或争用同一环境。

执行者会把修改情况和实际验证结果写回任务。如果遇到错误，也会记录原始错误和已尝试的方法，供后续调查或修复使用。需要改变需求或接口设计时，返回对应环节处理。

之后通常只需要说：

> 继续推进。

FlowForge 会根据更新后的任务、依赖和验证记录确定下一步。这里的“继续”可能是实施下一张票，也可能是处理审查发现或补齐阻塞任务所缺的信息；Agent 应说明它正在推进哪一部分。

**每轮你会看到：**已完成的修改、验证结果、当前卡点和下一步。你可以随时追问进度或纠正方向。

### 5. 审查交付，修复发现的问题

审查是 FlowForge 交付流程的一部分。你也可以主动要求一次独立检查：

> 对这个 proposal 的方案和实现做一次 review，检查有没有遗漏需求或违反项目规范的地方。

审查流程（Review）会确定本轮检查的变更范围，再分别核对两件事：实现是否遵守项目规范，以及是否满足当前有效的需求与设计。前端任务还会结合运行截图检查可见结果，不能只凭代码判断页面是否符合要求。

审查发现会变成后续工作：普通实现问题追加为修复动作，严重或影响下游的问题形成修复任务；如果涉及需求或设计变更，就返回相应环节。你可以接着说：

> 基于 review 的发现继续修复。

修复后再次验证和审查。交付满足要求后，负责收口的 Agent 记录完成证据并关闭任务，再检查 proposal 是否还有剩余工作。

**这一轮你会看到：**审查发现、处理结果和交付证据，包括实际运行的验证及对应变更。暂时没有可执行任务也可能是因为仍有阻塞，不能据此判断整个 proposal 已完成。

## 换方向或换会话时怎么继续

Proposal 保存了这项工作的需求、设计、任务和证据，你可以用它作为继续工作的入口。

| 你要做什么 | 可以这样说 | FlowForge 如何接续 |
|---|---|---|
| 调整需求 | “导出还需要支持脱敏，先分析影响。” | 更新需求，复核受影响的设计、任务和实现 |
| 拆开过大的工作 | “把下载管理单独建一个 proposal，后面再做。” | 分清两个提案的范围，保留有效结论并调整依赖 |
| 查看进展 | “这个 proposal 还有哪些没完成？卡在哪里？” | 根据任务状态和证据列出剩余工作及阻塞原因 |
| 反馈人工检查结果 | “我人工 review 发现，后台导出仍然用了提交时的权限。” | 核对实际行为与已确认的要求，记录问题并安排修复 |
| 换一个会话 | “继续推进数据导出 proposal，路径是……” | 读取已有文档和执行记录，核对当前代码后接手 |

你负责目标、取舍和对结果的判断；Agent 负责把决定落实到文档、任务与实现中。无需每次重新描述整段历史，但应提供明确的 proposal 名称或路径，便于新会话定位。
