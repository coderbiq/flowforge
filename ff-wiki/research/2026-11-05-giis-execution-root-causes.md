# GIIS proposal 长时执行：模型、流程、返工与环境的独立归因

日期：2026-11-05。统计快照：`2026-11-05T06:51:36.840916Z`。

研究问题：不预设测试过多，从真实 PI 会话判断长时执行是否来自模型更换或能力下降、FlowForge 设计、交付质量、环境或其他因素。

## 判断

近期样本最有证据的解释是：**复杂任务经过大量模型决策与角色交接，首次合同和实现中的错漏在后续暴露，触发重复取材、修订、冻结和审查；较慢且更长的主会话响应放大了这个过程。** 部分小修复的验证范围失衡，但测试程序本身不是足以概括所有长会话的根因。

- **模型更换：历史响应身份确实变化，近期无法识别实际后端。** 10 月同一 `group/pro` / `group/flash` 别名下出现多个返回模型名称；11 月样本失去 `realModel` 和 `responseModel`，不能据别名断言没换，也不能断言换成更弱模型。
- **模型变慢：近期 Policy 主会话有证据，实现子代理没有一致变慢。** 输出规模、角色、思考档和上下文必须分开比较。
- **模型能力下降：未证实。** 有具体执行错误，但缺少同任务、同环境、同提示与工具集的模型对照；错误数不能直接代替模型能力测量。
- **流程设计缺陷：有具体证据。** 小发现同样承担多角色完整收口、验收期间持续修改执行合同与测试基础设施、规则与工具能力不匹配，都会实际增加串行工作。这比“票数过多”更可验证。
- **其他原因：确实存在。** 跨模块业务约束、真实缺陷、测试脚手架错误、认证与后端启动、配置发布、检索失误、业务规则未定和用户暂停，性质与处理办法不同。

这里给出机制和证据强度，不给没有关键路径证明的“浪费占比”。

## 1. 样本与计时方法

主会话选取 9 个 migration 主题：10-19 staging PK、10-20 Finance、10-22 Policy 一致性、10-27 MBI、10-29 vendor 换源、11-02 附件 API、11-02 附件文件预迁移、11-04 文件预迁移续作、11-04 Policy 附件。对后五类中的 MBI、vendor、附件 API、文件预迁移、Policy 附件，另读取各自同名目录下全部 `**/session.jsonl` 子会话。

这是一组有目的的案例调查，不是所有 proposal 的随机样本，也不是只选慢任务后的性能基准。主会话可能横跨需求、设计、实施和验收，不能把整个会话称作纯编码时间；Policy 案例在快照时尚未结束。

- 使用实际 message，排除 system/注入背景。`durationMs` 是响应或工具执行耗时，不是墙钟跨度，不是纯推理时间。
- 跨文件用 `(顶层 timestamp, role, responseId/toolCallId/id)` 去重；本次五组父子样本重复数均为 0。
- 对每条有 durationMs 的 assistant/toolResult，以 `[timestamp-durationMs, timestamp]` 表示记录区间，合并父子区间，避免并行重复相加。
- **可观察活跃覆盖**指上述区间并集。它没有把隔夜空档算进去，也未用“超过十分钟就算离席”的任意阈值；但它可能包含工具内等待，不等于有价值工作时间，未记录的后台过程也可能遗漏。
- 模型区间和测试区间可并行，二者不能做互斥成本饼图。模型覆盖不证明每个模型都位于关键路径。
- 工具返回里的旧测试输出、票面重复引用的命令、不运行测试的 read/grep 均不能算新测试。本文不采用全文关键词命中统计测试次数。

## 2. 模型是否发生变化

### 2.1 历史别名确实对应不同返回模型名称

Finance 主会话请求名始终为 `group/pro`、high，但 945 条 assistant 记录中有：`glm-5.3` 573 条、`mimo-v2.6-pro` 325 条、`gpt-6.1-sol` 45 条、身份缺失 2 条。[F]

同一角色内的相邻返回也发生变化。例如 10-21 主会话第 6/8 行：请求别名未变，返回名称从 `glm-5.3` 变为 `mimo-v2.6-pro`；子 investigator 也有 `mimo-v2.6-flash` → `glm-5.3-flash` 的变化。[M1]

这些名称是服务端自报身份，并不独立证明实际部署权重。某些记录的 `responseModel` 有版本后缀而 `realModel` 没有，不能随意合并成已确认型号。

### 2.2 11 月存在身份观测缺口

独立调查扫描 10-19 至 11-05 创建的 68 个顶层会话及 537 个嵌套 JSONL，11-02 至 11-05 请求的 13,310 条 assistant 物理记录均缺少 `responseModel` / `realModel`；它们不是去重后的性能实验样本，只用于确认字段存在性。主会话逐日复核也显示，10-30 仍有实际返回名称，11-02 起所查样本只有别名。[M2]

当前安装的 pi-ai 只有在流中的 `chunk.model` 与请求模型不同且非空时才保存 `responseModel`；real-model 扩展也依赖服务端流字段。因此字段缺失可能来自回显别名、未提供字段或采集链变化。当前源码不能证明历史运行版本。已检查 `~/.pi` 的日志命名候选与 run-history，未找到能补齐近期型号的旁路记录。[M2]

**不能据此宣称“11 月换了某模型，所以降智”。** 若要确认，需要服务端按现有 responseId 回查路由和真实响应身份；本次没有访问服务端或修改任何配置。

## 4. 真正的工作量扩张：不仅是业务代码

去重后的父子样本：

| 主会话范围 | 子会话文件数 | 父子可观察活跃覆盖 |
| --- | ---: | ---: |
| MBI | 14 | 297.84 分钟，约 5.0 小时 |
| vendor | 32 | 604.83 分钟，约 10.1 小时 |
| 附件 API | 32 | 242.65 分钟，约 4.0 小时 |
| 文件预迁移 | 32 | 636.25 分钟，约 10.6 小时 |
| Policy 附件 | 107 | 787.13 分钟，约 13.1 小时 |

每列都覆盖相应主会话的多个阶段，不是同规模任务比较，也不是完成后的固定交付用时。子会话可能包含恢复及不同波次，不能当作独立 ticket 数。

Policy 的 107 份子会话包括：17 implementer、3 worker、21 investigator、16 planner、26 reviewer、12 reviewer-lite、12 executor。107 个子会话合计 4,352 次 assistant 响应，主会话另有 672 次，总计 **5,024 次模型响应**。调查和审查的工具调用分别达 1,648 与 986 次；角色名不等于“无效工作”，但这些数量展示了实际交付链的规模。[Q 的同名子会话目录]

附件 API 只有两张交付票，却经历 32 份子会话，包含重做规划、实施、复审与文档回填。这不等于应该把两票合一；它说明执行批次和交接远多于功能切片。

Policy 首轮需求/设计/规划期间，父会话本身产生约 191 轮响应、110.5 分钟响应时间；集中验收窗口 `11-05 01:26:18.470Z–06:20:25.999Z` 又产生 204 轮、185.5 分钟响应时间。[Q] **验收阶段仍在大量处理新发现、新合同与新工具，而非只等待一条测试命令结束。**

## 5. 有证据的根因与放大机制

### 5.1 需求与执行输入反复变化，其中有已证明的合同错误

- 附件 API 原设计职责被用户改为“接收文件内容并写入”，撤销意向台账和恢复；之后又纠正 ObjectStorageClient 入口。这些导致需求/设计多次修订。但初版 domain 落点本来受最初任务 R13 授权，第一次大修含上游口径重新分配，不能全算模型错误。[A0:5][A:19,76]
- 附件 API 单票草案原本已经包括 DDL/Mapper；后续分成数据库兼容升级和 API 两票，修正的是独立交付与发布前置的表达，**不是发现设计忘记改表**。[A:179,183,194]
- Policy 02 在批准图中要求验证主体＋附件＋凭据回滚，而凭据要由依赖 02 的 03 才创建；直到执行前 refine 才撤销这个前向要求。[Q:360,621,629] 这是“DAG 无环但验收语义有循环”的具体错误。IT 落位/命令也在此时更正；04 首轮修复仍有两项 partial，又修探针与规约负控。[J:21–27]
- vendor 发布时才发现名称超过真实列长、同码共享资源 payload 不一致、现表缺少五个回写字段，随后补 design rev2；Policy 05 实作后才发现根 DSL 为 80,565B，超过 65,535B 硬限，重拆 helper 后仅余 73B。[V:256,280,315][Q:839,870] 这是共享契约、物理落点、容量约束验证不足。
- 验收工具后续出现 JDBC DATETIME 类型转换、缺驱动类路径、不存在的 CLI 参数被用于负控等问题；这些属于工具和测试工程的返工。[Q:1040,1155,1159,1325]

调度还加了图中没有的屏障：01 在 10:00 已关闭，02 仅依赖 01，主会话仍决定等 04 收口；10:57 才开始 02 refine。[Q:360,483,613] 这 57 分钟内有 04 的真实工作，不能全算可节省时间，但 02 的准备本可与其重叠。08 最初依赖 05/06/07，用户要求逻辑先行后 06 与 08 机制实际并行，说明机制编码的开始条件与完整验收/真实执行条件不应混为一条阻塞边。[Q:360,883–904]

触发原因包括需求调整、事实/接口/测试接缝不够准确及真实实现缺陷；放大机制是每次修正又触发合同、角色权限、冻结、证据与审查更新。部分问题只有集成后才能发现，不能断言全部可在 Plan 阶段消除。

### 5.2 流程把不同风险的小改动收进相同的完整交付链

Policy 02 四项 Low 分别为步骤注释、缩进、英文注释与测试闭包提取。13:04 到 13:26 的收口经过 Plan、冻结、实现者、25 无库+4 IT+20 兼容测试和最终独立复核；业务执行语句未改变。[J:32–36][T02:81]

附件 API Fix 10 删除一行冗余校验，再执行两个模块的 cleanTest，共 1,650 项测试；定向验证错误消息有必要，但没有证据说明必须每轮重跑两个完整模块。[TA02:88]

当前 review 先要求 fresh Round 0，零 gap 后才进入并行双轴；fixable 包括 code smell，追加 Fix 后下个实现会话继续。implement 的五轮停止条件只覆盖**失败**修复，不能约束“每轮成功但不断新增小发现”的尾部。[R:66,116,150][I:61]

这里可确认的是**验证/审查批次与风险缺少足够区分、收尾缺少稳定边界**；不是“所有独立审查都无用”。

### 5.3 测试权限与角色工具能力不一致，制造额外交接

Plan 应负责预设测试，但后台 Plan 实际被 `protected test file` 拦截；后续通过能正常识别身份的前台 Plan 才完成，未改变测试保护规则。[J:24–25,50–55] 这是规则的宿主实现和执行入口不一致，不是用户业务难题。

只读 reviewer 无 shell 能力时，复验命令需要父会话代跑，再逐次 steer 回传 scoped diff、测试或内存反例。[Q:523–575] 权限隔离有目的，但在父会话响应较慢时，这条串行往返链成本更高。

此外，数次派发把 cwd 放进未部署根角色的子仓，找不到 agent 后又回根重派；证据路径、固定英文键、依赖分隔符与 checker schema 不一致也引发修订。[Q:790,918,1039,380,501–513] 部分是发布者漏遵守既定格式，部分是宿主限制；不能都叫业务缺陷或 checker 故障。

暂停等待用户的部分不能全部算成工具故障时间；活跃覆盖计时不将空档自动计入。

### 5.4 复杂能力与验收工具持续增加，导致“代码基本完成”仍离交付很远

Policy 附件范围涉及目标事务内关联、并发锁、提交凭据与恢复、staging 装载保护、源数据装配、目标结果回写、生成/注册兼容及发布门禁。它不是仅给 API 增加一个字段。[requirements.md / design.md / README.md，位于 QP]

07 验收工具冻结达到 v10；真正发现包括路径别名导致文件覆盖风险、缺依赖/缺工具时错误报告成功。解决这些问题有价值，但它们让后半程成为另一轮测试基础设施开发。[QP/evidence/07-plan-preset-tools-baseline-v1.json … v10.json；QP/issues/07、08]

真实宿主验收与业务选行/分类规则 Q-B/Q-C 仍未齐备时，整个 proposal 不能关闭，即使通用代码已完成。这是交付范围和业务前置的约束，不等于模型仍在写同一段代码。[QP/README.md:29]

### 5.5 工具、环境和等待是另一些案例的实质大项

- MBI 一次 configure 记录约 489.5 秒，另一次约 354.6 秒；一次后端健康轮询约 276.5 秒。[B:668,784,511]
- Finance 父会话记录的工具区间并集 265.86 分钟，远高于近期附件 API 父会话的 0.52 分钟。后者的大部分执行位于子代理，不能只比较父会话就说“Finance 环境慢 500 倍”。[F][A]
- Policy 一个实现子会话在全 GIIS 递归 grep 上停留数分钟，被中断后改为精确路径恢复；它不是业务测试失败。[Q:1434–1439]
- vendor 用户明确指出后端应该用现有启动脚本、认证应该用已修正的登录脚本；重新猜测已有环境入口造成了可避免排障。[V:971]

因此网络/数据量、配置发布、后端启动、工具使用错误需要分别计量，不能全部塞进“测试耗时”。

### 5.6 共享现场与自动提交增加恢复、取证成本

DataMigration 的 vault 自动提交导致 HEAD 持续变化，主会话曾因 `git status` 干净误判 04 尚未落盘，后由执行者纠正生成器和测试已在超时前写好。[Q:422,424,437] 多 proposal 共享生成规格也出现跨表漂移，必须改用单表片段移植；测试 XML 被后续筛选测试覆盖后，还要回读原始 toolResult 找证据。[V:118–122][Q:703,729]

这些因素解释了为什么交接时反复需要固定快照、逐字节/hash 核验和证据归档。fresh context 并不自动提供隔离工作树；减少交接前应先保证共享状态的归属与取证方法稳定。

## 6. 为什么不能判定“降智”

日志能证明具体错误：推荐与既定禁补绑冲突的路径、执行合同前向依赖、预检 NameError、夹具类型错误、权限入口不一致和过宽检索。它不能单独区分：模型能力、缺失或矛盾上下文、任务难度、长上下文、计划质量、工具定义、权限配置等原因。

目前没有同一任务的前后模型对照，也没有可信的每个模型首轮通过率分母。RED 预设故意失败，36 个失败可能来自一个 NameError，历史基线失败也不是本轮新增缺陷。拿这些数量宣称“模型降智”会误导优化方向。

已有反向证据：近期实现子代理没有普遍变慢；部分修复后只复跑受影响 IT，不重跑 224/7/44 套件。[QP/evidence/03-post-fix-mysql-it/09-run-record.md:61] 所以不能把问题全部归给模型、测试或 FlowForge 的任一单点。
