# FlowForge 要解决什么问题，以及如何解决

> 状态：第一轮讨论稿，供继续梳理产品定位。用户提出的核心观点、仓库可核实的机制、本文的解释及待确认判断分别说明；本文不替代现有需求和设计文档，也不引入新的实施任务。
>
> 日期：2026-10-26

## 1. 核心命题

用户提出的核心观点是：**在复杂项目中，通过提供精准的上下文，让 Agent 能够更好、更准确地逐步完成复杂需求的分析、设计和开发。**

据此，本文建议把 FlowForge 的核心问题进一步表述为：

> 在有限的有效上下文中，如何让 Agent 在复杂需求的每一步，都能获得当前工作所需的、已确认且适用的信息，并把结果可靠地交给下一步。

这里的“精准上下文”暂按四个条件理解：与当前工作相关；足以支持当前决策或执行；已确认的内容与未决问题有明确区别；引用的信息仍然有效。上下文短是手段，信息充分且可用才是目标。这一定义是本轮提出的整理方式，仍可继续调整。

FlowForge 的方案可以概括为：**在讨论中持续保存已确认的需求和设计，在任务准备阶段组织局部所需的信息，用有向依赖图确定推进顺序，再通过验证、审查和证据完成交接。** Skill 约束信息如何形成、整理和消费，CLI 检查可计算的结构与关系。[S1][S2][S3]

## 2. 问题如何在复杂项目中出现

### 2.1 讨论依赖长对话记忆，后续阶段难以完整继承结论

一个复杂需求通常要经过多轮需求澄清、方案比较、边界确认和实现讨论。重要信息分散在不同轮次：某个异常场景、一次否定的方案、一项兼容性要求，可能只在早期出现过。

用户指出，随着对话增多，上下文压缩会使这些内容丢失。更具体的工程风险是：后续阶段没有可靠入口确认哪些结论仍然有效、哪些设想已被否定、哪些问题尚未决定。设计可能遗漏需求边界，实施可能重新选择已经讨论过的方案。

因此，只在需求分析结束后补一份总结仍有风险：生成总结时，早期细节可能已经不在可用上下文中。FlowForge 的 Align 约定是在每项需求决定确认后直接更新权威文档，替换已失效的含义，而非不断追加聊天历史。[S2]

### 2.2 信息写进文档，仍然不等于执行时能准确使用

即使需求、设计和规范均已保存，执行一个局部任务时，Agent 仍然需要判断：

- 哪些需求条款与这次修改有关，哪些边界必须保留；
- 采用的是哪版设计，哪些接口和顺序已经确定；
- 哪些项目规范适用，哪些只是其他模块的约定；
- 应该修改哪些位置，如何验证结果。

文档越长、信息源越分散，这些判断越容易遗漏。简单地把所有文档放进上下文，也会增加阅读负担，并消耗本应用于理解代码和执行任务的空间。

用户的判断是：不能把复杂项目的可靠交付寄托在执行 Agent 每次都能自行找到全部适用信息上。本文建议把这一点写成产品设计前提：**应在任务准备阶段完成信息选择和组织，减少执行阶段反复搜索、重新解释和临时补决策的负担。**这不表示 Agent 无法搜索，而是把搜索和解释放到更适合承担它们的环节。

### 2.3 任务清单缺少上下文和依赖，无法直接指导可靠执行

“实现重试机制”这样的任务名称并没有回答重试哪些错误、是否有次数上限、是否需要幂等、是否兼容旧数据、如何证明行为正确。任务切得小，也不代表这些问题已被解决。

复杂项目还存在顺序问题：某项任务必须等待接口或数据结构形成，另一些任务可以独立推进。如果这些关系只存在于主会话的记忆里，换一个会话或执行者就需要重新推断。

因此，交付单元需要同时具备局部充分的执行信息、真实的阻塞关系和可观察的完成条件。FlowForge 的 Ticket 与 DAG 分别承载这两类信息。[S3][S4]

### 2.4 交接若只靠口头汇报，进展与错误会一起丢失

新的 Agent 不仅需要知道“下一步做什么”，还需要知道上一步实际完成了什么、验证过什么、失败时试过什么。只有“已完成”或“遇到问题”的回复，难以支撑下一次执行与审查。

FlowForge 通过 Implementation note、Blocked evidence、Review rounds 和 Completion evidence 保存执行结果与处置情况，使后续上下文有持久入口。[S5]

## 3. 问题与解决机制的对应关系

| 具体问题 | FlowForge 的机制 | 预期作用 | 主要责任方 |
|---|---|---|---|
| 多轮对话后，已确认结论难以继承 | 需求与设计作为持久权威；确认后更新正文 | 后续工作可以从文件恢复有效结论 | 人与分析、设计 Agent，受 Skill 指导 |
| 文档很多，执行时难以找全相关信息 | 在 Ticket 中写局部设计摘要、变更、约束、位置和验证方法 | 减少临场检索和重新推断 | 规划与任务准备环节 |
| 通用规范难以准确应用到具体任务 | 识别适用规范，转成明确条款，再转录到任务 | 执行者直接获得适用约束 | Align → Design → Plan |
| 任务缺少具体事实，执行时被迫猜测 | 准备已核实的契约、场景、测试、产物同步关系和约定 | 把事实缺口尽量暴露在开工前 | 任务细化与开工检查 |
| 执行顺序依赖会话记忆 | 显式 DAG、`check` 和 `frontier` | 根据已声明依赖计算可推进任务 | Agent 声明关系，CLI 计算 |
| 长会话累积过多历史，难以交接 | 每票一个新的执行上下文，从持久工件开始 | 控制一次执行所需的信息量 | 调度与执行约定 |
| 上游含义变化，下游仍使用旧信息 | revision、`consumes` 与引用诊断 | 提醒下游复核适用性 | Agent 维护语义修订，CLI 检查声明 |
| 勾选任务不能证明交付正确 | 验证、双轴审查、完成与失败证据 | 给下一步提供可检查的实际结果 | 执行和审查 Agent |

这里需要区分“机制存在”和“效果已被证明”。上表描述的是当前方案及其预期作用，不代表已经测得需求遗漏率、返工率或成本下降。[S1]—[S8]

## 4. 方案的关键：把上下文准备前移

### 4.1 从对话中提炼有效结论

需求文档保存问题、可观察结果、范围、场景和约束；设计文档保存责任、接口、信息流、迁移和验证策略。两者保存当前有效的含义，不要求保留所有讨论过程。[S1]

这样，进入设计阶段时可以读取已确认的需求；进入任务规划时可以读取已确认的需求和设计。恢复工作不必依靠某个会话是否仍记得早期对话。

这也意味着，“分析、设计之后生成任务图”只是整体方案的后半段。前半段是在分析和设计的多轮对话中持续沉淀有效信息，否则生成任务时仍然可能缺少来源。

### 4.2 把全局信息整理为当前任务所需的局部信息

任务文档应回答：交付什么、与当前工作有关的设计是什么、在哪里修改、按什么步骤修改、遵守什么约束、如何证明完成。

它不需要复制所有上游讨论。共享权威继续保存全局含义和来源，Ticket 保存本地需要的摘要、动作与条款，并链接回来源。这样既能降低执行阅读量，也保留了核对依据。[S1][S3]

规范处理体现了同样的思路：适用性在前面识别，设计阶段形成明确的 `must` / `must not` 条款，规划阶段按约定转录到任务。执行阶段检查转录状态，而不是重新解释整个规范库。[S3][S5]

当前 Plan 约定只发布执行细节的骨架，再由任务细化环节核实仓库事实、填入内容。因此，“任务文件已经生成”和“任务已具备充分执行信息”是两个不同的事实。[S3]

### 4.3 用依赖图控制推进，用证据支撑交接

上下文说明如何完成当前工作，DAG 说明当前工作是否还依赖其他任务。`check` 检查图及工件关系，`frontier` 根据声明的依赖与诊断投影出可推进队列。[S3][S6]

执行后，实际验证结果、审查发现和失败事实写回持久工件。后续执行者可以从这些文件继续，而不必继承整段聊天。审查发现也会进入修复流程，使未解决问题保持可见。[S1][S5]

## 5. “只看一个文档”需要如何表述

用户希望每个任务包含实现所需的需求、方案和规范，使 Agent 可以从较小的上下文中获得信息。这是本轮最重要的目标之一。

建议将其表述为：

> **以任务文档为主要入口，提前提供执行所需的局部上下文和明确来源，使 Agent 在受控的上下文范围内推进任务。**

当前实现约定尚不能表述为“执行时绝对只读一个文件”。Implement 仍要求读取项目不变量、任务、链接的需求与设计权威及其消费版本，执行时也必须读取相关代码。[S5]

因此，当前机制更准确的效果是减少无边界检索和临场推断，并为必要阅读提供坐标。是否进一步追求执行 Agent 无需回读上游需求、设计，是一个需要继续确认的目标；它会影响任务内容密度、同步成本和核对方式。

## 6. Skill 与 CLI 分别承担什么

**Skill 承担需要理解和判断的工作。**它指导 Agent 澄清需求、形成设计、识别规范、提取任务上下文、核实事实并审查交付。Task 的语义是否充分、规范是否选对、设计是否满足需求，仍依赖这些活动的质量。

**CLI 承担可以按声明确定计算的工作。**它检查依赖和引用、比较消费版本、识别部分执行契约缺项、检查规范标记及完成证据是否存在，再生成队列和诊断。[S6][S7][S8]

例如，当前规范检查实现明确只验证标记和状态，不解析条款内容；版本检查比较声明的 revision，不会自行理解一段业务含义是否变化。上游版本落后产生 warning，其语义影响仍需复核。[S7][S8]

由此不能推出“只要 check 通过，任务就语义完整”或“没有依赖边就可以安全并发写同一批文件”。任务含义、漏声明的依赖、写入冲突和集成行为仍需要相应的准备与验证。精准上下文降低遗漏风险，不能替代正确需求、合理设计和实际验证。

## 7. 一个示意场景

以下示例仅用于解释机制，不是 FlowForge 新增需求。

假设团队要为消息发送增加重试。多轮讨论确认：仅对暂时性错误重试；永久性错误立即结束；重复请求不能产生重复发送；需要保持旧配置兼容。

如果这些结论只在聊天或长文档中，执行“增加重试”任务时，Agent 可能只实现了循环和间隔，却漏掉错误分类或幂等边界。

采用上述方法，相关结论先进入需求权威，设计再确定错误分类、幂等检查和重试调度的责任与顺序。任务准备阶段把相关边界、具体修改位置、适用规范以及成功和失败验证写进执行任务。如果重试调度必须依赖错误分类能力，该关系作为阻塞边进入 DAG。

接手执行的 Agent 从任务获得局部入口，按明确位置读取代码并实现。验证和审查再检查暂时错误、永久错误、重复请求与配置兼容是否符合有效约定。新会话继续时，读取持久结论和证据即可恢复当前工作。

## 8. 下一轮需要收敛的判断

### 8.1 核心承诺覆盖到哪里

建议把“需求分析、设计和开发之间的上下文连续性”作为核心问题；任务级执行上下文是其中最具体的一项解决机制。这样产品定位能解释为何需要 Align 和 Design，也能解释为何仅有任务图还不够。

待确认：是否接受这一范围，还是希望把核心承诺集中在“把既定需求和设计交付给执行 Agent”？

### 8.2 任务独立性应达到什么程度

当前约定支持任务为主要入口，并保留上游权威核对。用户描述还包含一个更强目标：执行时尽量从一份任务文档中获取所需需求、设计和规范。

待确认：后者是希望强调的使用目标，还是要作为严格约束——执行 Agent 无需再回读上游需求与设计？这一问题决定后续如何评价当前方案是否充分。

### 8.3 如何检验方案有效

以下是候选评价方式，尚非已经取得的结论：

- 新会话能否从持久工件恢复当前任务，而无需用户重讲已确认结论；
- 执行中因需求、设计或规范信息缺失而暂停、猜测和返工的情况；
- 审查中发现的需求遗漏、约束违反及其返工量；
- 单任务阅读范围和上下文消耗，以及准备这些上下文本身的成本。

评价应同时考虑上下文准备成本与交付质量，不能只统计任务文档变短或执行模型变便宜。
