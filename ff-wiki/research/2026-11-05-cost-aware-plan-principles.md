# 成本感知的 Plan 与修复复验原则（讨论草案）

日期：2026-11-05。本文整理已确认的约束和建议，尚未修改已部署技能、CLI 或执行中的 GIIS proposal，不作为其新的验收权威。

## 已确认的边界

- 优化重点是实施阶段的实际耗时；需求分析、设计、Plan、Refine 继续保留。
- 轻量执行者继续机械执行，不自行设计、不修改验收标准、不擅改预设测试、不自行豁免失败。
- 保留独立审查、测试保护、事实证据和真实缺陷的阻塞作用；不能假设新模型不会再改测试凑通过或偏离需求。
- 成本判断前移到 Plan/refine 和有权裁决的 Review/设计责任方，执行者只遵循明确命令。
- 优化目标是完成既定交付的总耗时，包含验证、环境准备、角色交接和返工；测试数量和审查轮数只是观察指标。

## 建议写入规则的八条原则

### 1. 按最低充分证据分配验证责任

每个验收行为由最便宜且确实能证明它的检查负责。每票保留足以证明本票 Delivery 的定向测试、必要编译和关键反例；跨票关系在明确的阶段集成验收中证明。

“轻量”不等于只查文件存在或只跑 happy path。若本票交付的是事务回滚、真实数据库兼容或公共接口约束，不能用无法证明这些行为的 mock 替代必要验证。

### 2. 在 Plan 时明确阶段集成验收

把相关票组成可以实际接通的阶段，在该阶段末安排集成验收，并在部署/真实使用前完成必需门禁。无需等整个大 proposal 的所有功能写完才首次集成。

每条阶段级验收必须有执行归属、命令/方法、前置、通过条件和失败处置。票只声明自己的真实交付；阶段门禁未通过，不能声称阶段或 proposal 已验收。

局部票的 Done 不再包含被明确归属阶段的全链路要求；如果此前已包含，须由有权责任方先修正有效合同，而非执行者跳过。后继依赖的关键契约在被消费前仍须成立。

### 3. 同一有效版本不重复执行同一重验证

在阶段内共用的完整模块回归、数据库初始化和重型集成场景，由明确的验收任务执行，其他票引用结果及适用范围。跨版本不可盲目复用。

后续修改是否使证据失效，由裁决者依据受影响代码、测试、配置与环境判断。无法确定失效范围时，保守重验；不要求轻量执行者自主判断，也不先建设复杂的自动依赖推断系统。

### 4. 按可验证的修改组执行检查

一个必须一起修改才成立的接口和调用方是一组机械 Change；Plan/refine 明确组末编译与验证，不强制在半完成状态反复构建。

Done and verify 的全组检查在所需范围完成后执行，不因同一命令被多个 Change 引用就重复运行。执行者不能自行合并、跳过或改变这些分组。

### 5. 修复合同必须带有定向复验范围

Review 裁决每批 Fix 时同时明确：原发现、允许改动、必须复验的行为、可复用证据及扩大验证的条件。涉及预设测试修改时仍交给合法测试作者。

这是拟增的复验规划规则。当前 Review 的 Fix 规划权不等于可以任意删减 Done and verify；需明确区分“同一验收标准下复用未失效证据”和“改变验收标准/验证策略”。后者仍交回相应权威，不能通过一份简短 Fix 绕过。

| 已裁决的修复类型 | 默认复验方向（须由责任方给出具体命令） |
| --- | --- |
| 普通注释/格式且无行为、生成或工具消费影响 | 差分与规范检查；有语法影响时编译；独立确认未改变执行语义，不自动重启数据库或全链路 |
| 局部分支或输入校验 | 原失败用例/反例及直接受影响单元；共享行为受影响则扩大 |
| 测试/fixture 修订 | 合法作者改动及独立断言完整性核查，重跑受影响测试；不以修改断言掩盖产品失败 |
| 公共接口、DDL、事务、生成器或共享配置 | 受影响消费者与真实接缝验证；可能立即需要集成测试，不能一律拖到阶段末 |

修复后的独立审查继续存在，但未失效结论不从头取证。普通文档若是代码生成源或运行配置，不得按“只改注释”处理。

### 6. 首轮审查覆盖完整范围，复审关注修复与影响面

第一次在同一固定版本上汇齐完整发现，保留各轴独立判断；有共同写集或验证面的发现合并成修复批次。

复审检查旧发现是否关闭、修复是否引入新问题、其他验收结论是否仍成立。发现新的真实缺陷仍须处理；不因追求少轮数而隐藏失败，也不因为重新启动审查就无依据增加交付要求。

对没有具体失败路径、只表达个人设计偏好的建议，不转为强制 Fix。已约定的硬标准仍须修正，不能仅凭 Low 标签豁免。

### 7. 用可执行反例提高首轮修复完整性

Plan/refine 把易漏条件写成可观察结果和明确反例；Review 给轻量执行者的 Fix 也要同样精确。

例如“校验键组成正确”不足以支持机械实现，应明确“缺任一规定组分失败、交换规定顺序失败、完整原序通过”。这能减少“修了但仅 partial”的再修复，不扩大执行者设计权限。

机械可检测的规范问题尽量在审查前一次检查、批量处置；没有可靠工具的语义检查仍由审查承担，不以更多模板文字假装实现约束。

### 8. Plan 对重型验证和额外交接给出简短成本说明

不要求精确预算或风险评分。对需要整模块回归、启动环境、创建验收工具、重新冻结或新增角色往返的项目，至少说明：为什么必须在这里发生、可否共享/延后到阶段、预计的主要成本来自哪里。未知运行时间写未知，不能编造秒数。

复用现有命令和验收工具优先；确需新工具时把它的开发、最小自验证和维护成本纳入计划。避免修复时顺手扩展工具能力或文档承诺，给自己增加与既定交付无关的证明义务。

## 用一个小表表达验证安排

可在现有设计/Plan 中保留一份阶段验证表，各票 Done and verify 引用相关部分；不要为这些原则给每张票再复制一套长模板。

| 交付 | 本票必须证明 | 阶段验收负责 |
| --- | --- | --- |
| 数据结构兼容扩展 | 升级/旧数据兼容的必要验证 | 与实际写入和读回链路接通 |
| 文件写入 API | 输入保护、保存返回值和错误传播等定向验证 | 真实文件登记→写入→读取及跨模块失败行为 |
| 调用方接入 | 命令映射、状态处理、必要关键反例 | 与上述两个交付的完整业务场景 |
| 阶段集成验收 | 固定版本上的集成场景及必要模块回归 | 通过前阶段保持未验收 |

这是责任划分示例，不表示前三票都可使用纯单元测试；验证方法必须与本票声明的交付相符。

## Review fix 轮数：已证实的原因与计数边界

1. **审查阶段数不等于修复批次数。** Policy 02 记录 Round 0→1→2，其中只有一批 Fix7–10；04 记录 Round 0→1→2→3，其中有两批实际修复。不能把轮次标题或 reviewer 数直接当缺陷反复修复次数。[1][2]
2. **确有修复不完整。** 04 首轮 Fix 后，旧表探针依赖尚不存在的列、键校验只比集合且条件性检查关键组分，产生两项 partial；后续用明确反例补齐。这类复审有效，优化点是修复合同精确性。[2:353]
3. **确有小改动重复承担较重收口。** 02 的四项 Low 是编号、缩进、注释语言、测试回调组织，Spec 已零发现；修后仍实际跑 25 无库、4 MySQL IT、20 兼容测试并进行独立复审。硬标准应修正，但复验范围可以更精确。[1:275]
4. **验收工具及承诺扩张产生后续证明义务。** 路径保护、Schema 校验及缺依赖分类中包含真实缺陷，也包含工具本身的错误和新增覆盖要求。不能一概称作 reviewer 挑刺，也不能每轮顺手增加未约定能力。[3:5.4]

历史核对补充：`eaa1f1d`（2026-08-27）建立轻量实现—独立 Review—Fix 再执行的显式循环；`f50dfcc`（09-09）增加 substantive finding 的 repair 生命周期；`c962d15`（09-13）加入双轴前串行 Round 0。这些主要控制在 8–9 月已经存在，不能仅凭 11 月执行较慢就解释为最近突然增重。

Round 0 的原始设计恰是用廉价逐项审计挡住轻量执行者的假完成和 partial，减少昂贵双轴反复证伪。[4] 因此保留它的可靠性目的，本草案只提出明确复验范围、证据复用和修复批次；不以计数减少证明质量改善。

当前证据能解释这些案例的轮次，不足以给出同规模任务在不同历史版本的修复率增长。历史文档记录 09-12 样本也存在多轮审查，但项目、规模、工具和计数口径不同，不能据此否定用户的近期观察，也不能据此计算增幅。

## 落地范围与验证办法

若采纳，主要调整 Plan/refine 的验证分配、Implement 的检查执行时机、Review 的 Fix 复验合同；测试权限和轻量执行边界保持。

技能、共享契约和 CLI 的验收/关票解释必须一致，不能只在提示词里说“阶段末再测”。先用一个真实阶段验证方案是否可表达和可执行，再决定是否需要机器字段；本草案不新增 schema、状态或 CLI 签名。

比较同一阶段的实际活跃耗时、重验证执行次数、环境启动次数、修复派发批次、partial 复发和遗漏缺陷；仍保留各审查轴结果。减少程序运行不应换来更多后期返工。
