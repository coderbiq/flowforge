# 成本感知的验证规划与修复复验：需求

<a id="purpose"></a>
## 目的与依据

降低 proposal **实施阶段**的重复验证、环境准备、修复派发及重复取证成本，同时保持轻量执行者的可靠性约束。需求分析、设计、Plan、Refine 的必要性不在本次优化范围内。

GIIS 已观察到小范围修正重跑较大验证集、修复说明不充分导致 partial 再修，以及验收工具本身返工；这些是本需求的事实依据。模型能力下降、所有 proposal 的修复率同比上升、可节省的固定百分比均未证实，不作为需求前提。来源及用户已确认边界见 [来源归类](source-notes.md#accepted-boundaries)。

<a id="reliability"></a>
## R1：可靠性边界保持

- 轻量实现者继续机械执行，不自主设计、不修改验收标准、不擅改预设测试、不自行删减验证或豁免失败。
- 测试作者与实现者的权限边界、独立 Round 0 与 Standards/Spec 双轴审查、真实缺陷的阻塞作用继续保留。
- 不以 Low 标签、轮数或时间预算自动接受缺陷；旧证据不适用时不能借“节省成本”继续关票。
- 新的成本安排由有权规划、裁决的角色确定，不能依赖执行模型能力提升。

<a id="allocation"></a>
## R2：每项交付都有充分且不过度重复的验证责任

每票必须证明自己的交付及供后继消费的契约；跨票组合行为可以由明确的阶段集成验收承担。不得将证明本票承诺所必需的验证移走，也不得让局部票承诺后继才会产生的能力。

“轻量验证”指能证明目标行为的最低充分检查，不等于只检查文件存在、语法或正常路径。事务回滚、数据库兼容等交付仍需与承诺相符的真实验证。

阶段验收必须有归属、前置、观察方法、通过条件和失败处置。它在相关功能接通后、需要完整证明的发布或实际使用前执行；未通过时不得声明阶段/整体通过。局部通过不自动等价于阶段通过。

<a id="cost"></a>
## R3：Plan 显式考虑实施总成本

对于整模块回归、环境启动、新验收工具、重复冻结及额外角色交接，规划产物应给出简短理由：为什么在这里执行、是否可共享或放到阶段、主要成本是什么。

优先复用既有工具与有效证据。没有测量值时标为未知，不编造耗时、不要求风险评分或精确预算，不为成本规划额外制造大量模板与重复文档。

<a id="groups"></a>
## R4：机械执行遵循预先指定的检查时机

允许将必须一起修改才成立的 Change 作为一组，在规定位置编译和验证，避免对半完成状态进行无意义检查。执行者必须获得明确的 Change 范围、命令、预期和执行时机，不能自行合并或跳过。

同一有效版本上的一次真实执行可以支持多个明确覆盖的 Change；每条 Change 的完成证据仍需可定位，不能将一次执行记为多次实跑。

<a id="fix"></a>
## R5：小修复获得与影响范围匹配的复验

有权裁决的 Review 为 Fix 明确必须重新执行的检查、拟复用的旧证据、扩大验证的条件。普通注释/格式修正不能自动触发数据库及全链路重验；影响公共接口、事务、DDL、生成物或共享配置时必须覆盖实际影响。

复验范围调整不改变验收目标。改变验收标准、验证策略或预设断言时，仍由原权威及合法测试作者处理；沿用现有 design return / repair 规则。

<a id="evidence"></a>
## R6：证据复用必须诚实且可独立核验

复用必须指向原执行记录、适用版本和覆盖对象，并说明当前变更为何不使其失效。命令相同、旧记录曾经成功或文件哈希存在都不能单独证明可复用。

独立审查确认复用成立后才能关票。证据缺失、相关输入变化且影响不明、验收工具可信性变化时，需要补验或阻塞；不得复制旧 exit=0 冒充新执行，不得削弱测试获得通过。

<a id="review"></a>
## R7：保留审查层次，减少可避免的修复往返

同一固定版本上已经明确的发现应合并为完整、机械可执行的修复批次；Fix 要写清关键失败条件和反例，降低 partial 复发。普通规范问题可用可靠工具提前检查，但不能用工具通过替代语义审查。

复审必须确认旧发现已关闭、修复未引入新问题、其余交付仍有有效证明。新真实缺陷继续处理；个人偏好、未证实的假设或顺手扩展的工具承诺不能无依据变成新验收要求。

<a id="compatibility"></a>
## R8：既有票与门禁兼容

无新验证安排的旧票保持既有执行规则，不因升级自动减少验证。采用新安排需由权威角色明确修订，执行者不得临场解释迁移。

不改变既有 ticket 状态、Issue Schema 头、CLI 接口签名及测试保护。CLI 检查仍保留，但不被宣传为能够证明验证充分性或证据语义有效性。

<a id="measurement"></a>
## R9：改善效果用实施阶段结果判断

验证方案是否降低同类阶段的实际活跃耗时、重复重验证、环境启动和修复派发；同时观察 partial 复发、遗漏缺陷和重开。审查调用数、Fix 批次数、同一问题复发次数分别计数，不把 reviewer 数或 Round 标题数当成修复率。

不承诺固定提速比例；减少运行次数但增加后期缺陷或伪造通过，不构成改善。

<a id="scenarios"></a>
## 代表性验收场景

| 场景 | 期望结果 |
| --- | --- |
| 多票共用重型集成检查 | 局部票验证自身承诺，组合验收有唯一明确归属；发布不会绕过它 |
| 接口声明与调用方必须一起改 | 按权威给出的修改组完成后验证，不在中间半完成状态制造阻塞 |
| 只修普通注释/缩进 | 定向检查和独立复核满足原标准，未失效的集成结果可有据复用 |
| 文档是生成输入或修复影响事务/Schema | 不按普通文案处理；按实际影响扩大验证 |
| 旧证据所依赖配置已变或版本不明 | 不复用；补验或阻塞，不能直接关票 |
| Fix 只验证了键集合，没有验证规定顺序 | 预设反例能暴露 partial，不能由执行者修改断言消除失败 |
| 集成门禁已通过，后续修复使证明失效 | 新版本的发布重新受所需验收约束，不能沿用过期通过 |
| 旧票没有采用新安排 | 按旧命令和检查时机执行；升级不产生隐式省略 |

<a id="scope"></a>
## 范围与排除项

本轮需求覆盖验证责任分配、执行检查分组、Fix 定向复验、证据复用及其部署/验证一致性。下一步由设计决定具体落点。

不包含取消 Plan/Refine、默认切换 full mode、放宽轻量模型权限、取消 Round 0/双轴审查、改变 repair 路由、模型选择/降智评测、通用调度平台、自动证据缓存或依赖推断平台，以及批量改写正在执行的 GIIS proposal。
